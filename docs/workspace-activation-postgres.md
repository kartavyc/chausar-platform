# PostgreSQL activation and candidate custody

`workspace-activation-postgres.ts` implements the existing `WorkspaceActivationPorts` and `WorkspaceBackupActivationPorts`. It reuses `WorkspaceActivationHost` for business projection and review, `WorkspaceBackupActivationHost` for independently authenticated v2/archive/material derivation, and `WorkspaceActivationLocalCustody` for encrypted staging, paired activation/candidate claims, exact physical publication and filesystem restart inspection. It changes no Engine, Vault, shared codec or existing file behavior.

The storage dependency is lane A's `WorkspacePostgresCustody`, qualified separately at `c35a1451bbea657a40ac011c1f6ade17cfdbcfc8`. Its SQL preparation lives outside ordinary authority. The adapter refuses ordinary loads for unpublished custody. No PostgreSQL client, credential, path, storage adapter or callback is accepted from an RPC payload.

## Constructor contracts

`createWorkspaceActivationPostgresPorts(options)` returns `WorkspaceActivationPostgresCustody` with `.ports` and `.targetPath(targetId)`.

| Capability | Root obligation |
| --- | --- |
| `sourceVault`, `journalVault`, `applicationDirectory`, `budgets` | Actual unlocked PostgreSQL source, distinct durable encrypted journal, canonical application directory and positive complete filesystem/native-envelope budgets. Existing local path and budget validation remains active. Root owns journal credentials, retention and lifetime. |
| `source.withSource(context, expectedInventory, work, candidateId?)` | The existing local source contract: hold the Vault snapshot/current complete-owner/readiness and actual independent namespaces through the callback and final assertions. Acquire the Vault queue before native SQL custody. Source capture itself must already use the correct native adapter lease, e.g. B's `withHeldSource`; the new module's native wrapper then nests through that SAME adapter. Do not reacquire the Vault queue from a held callback. |
| `nativeSource` | A's custody built from the exact adapter installed in sourceVault. The module holds its native lease inside the already-held Vault callback through publication and final readback; native Vault ID and revision must match the supplied Vault snapshot. |
| `candidates` | Existing independently authenticated candidate reader and whole-callback exact issuance exclusion. `WorkspacePostgresActivationCandidates` supplies these methods. Its held reader must not reacquire source or candidate exclusion. |
| `targetCustody(targetId, targetDirectory)` | Resolve A's actual stable constructor-installed target adapter/slot and the exact canonical directory supplied by this module. Target slot must differ from source and actually be absent. The existing independently source-encrypted physical `wit_<sha256(targetId)>_reservation` remains required. Coordinator owns issuing that reservation against actual empty SQL/physical custody, adapter lifetime, current target admission and Engine/open selection. |
| `bootstrap.allocateAuthority(context, target)` | Existing fresh owner/workspace/context/session allocation. It does not publish authority. |
| `bootstrap.prepare({stagingDirectory, publication, storage})` | Initialize exactly the validated fresh revision-zero State using the supplied A `createPreparedAdapter(reservation)` and a new root credential; close the Vault before returning `{liveFiles,qualification}`. `liveFiles` may be empty for SQL-only authority, but must declare every actual closed live file. The module independently obtains the prepared proof/envelope and adds `live/postgres-publication.encrypted.json`. No historical key/session is copied. |
| `bootstrap.inspect({targetDirectory, publication, inspection})` | Authenticate fresh target Vault identity, exact initial State/authority, current owner/readiness and explicitly allowed later live lineage. During preparation inspect exact original ciphertext using a constructor-only read-only adapter; during recovery authenticate actual current committed authority. Return exactly `{authorityCiphertextBytes,authorityKind:'adapter-issued-envelope'}` measured from the authenticated current Vault capture. Never publish, retry, adopt or attach an Engine. Root must hold the actual target read/write admission needed by its current-live inspection. |

The same source/target/candidate process lock identities and source-encrypted physical reservations as the existing local publisher are retained. SQL custody operations compare storage generation, slot creation, operation ID, publication creation, Vault ID, revision and encrypted-envelope digest. Continuous exclusion of ordinary target SQL writers is a root admission obligation; per-call SQL inspection is not claimed to certify arbitrary cross-process target isolation.

Construct target adapters before entering a source transaction: initialization can require schema locks. B's complete database capture retains relation SHARE locks and global namespace fingerprints. Do not keep that database-wide capture fence around target INSERTs in the same database: target custody/authority writes conflict with those relation locks and intentionally change the control-table inventory. Coordinator must use a separately installed target database or an explicitly reviewed activation source/namespace profile that preserves current source-row/business custody while authenticating authorized target/control transitions. This is a shared-join/native qualification concern; this module does not bypass B's inventory assertions or weaken capture exclusion.

`WorkspacePostgresActivationCandidates(options)` requires the same source/journal/application/native/source capabilities plus `maxCandidateBytes`. It supplies `readCandidate`, `readCandidateHeld` and `withCandidate`. `readCandidate` acquires source admission; `readCandidateHeld` and `withCandidate` are for a caller already holding that admission. Their native source lease nests through A's existing adapter transaction. `withCandidate` supplies an already-locked reader.

Its `backupActivationPorts(originals)` returns the unchanged `WorkspaceBackupActivationPorts`. Root `originals.withTransaction` supplies all existing original lease methods except `createCandidate` and `readCandidate`, retaining the actual source/archive/export/inert/empty-target fences for the entire callback. The module adds native source custody and candidate exclusion, then installs its own durable creation/read methods. Root must not acquire that candidate lock itself or invoke the source-acquiring public candidate reader from inside the callback. The caller passes these ports to `WorkspaceBackupActivationHost`; this is not a second archive/candidate algorithm.

## Publication and uncertainty

The existing atomic local ledger consumes both activation ID and candidate creation before bootstrap begins. The separate encrypted PG journal first retains the chosen operation/creation IDs, exact source storage/incarnation/authority digest, target storage and immutable publication digest. Only then does A reserve the actually absent SQL slot and empty physical directory. A lost reservation acknowledgement is inspected by the journaled IDs through `inspectOperation`, never reserved again.

Root bootstrap writes only prepared encrypted SQL custody. The module independently authenticates it, writes/syncs the original encrypted-envelope file, and persists the exact SQL proof/digest and original file generation in its journal. It rejects byte-identical file replacement as well as ciphertext alteration. The existing local publisher persists its full prepared manifest, publishes every physical entry without overwriting, authenticates the fresh live profile and commits the encrypted filesystem marker. A then publishes the exact SQL proof once. A final PG journal acknowledgement marker is optional evidence of acknowledged completion, not a substitute for either store's authentication.

Prepared admission is scoped only to the original local commit. Immediate and restart readback require committed SQL. Lost filesystem acknowledgement leaves SQL prepared and ordinary open unavailable. Lost SQL acknowledgement can resolve committed if the independently committed filesystem marker, exact original encrypted evidence, SQL creation/proof and actual current target all authenticate. Inspection does not write a completion marker, replay publication, overwrite, adopt or delete anything. If either half is absent, reserved, prepared, replaced, corrupt or uncertain, public inspection returns the existing exact `{status:'unknown',activationId,reasonCode}` shape. Current source authority/owner/readiness changes refuse admission explicitly.

The PG journal and candidate ledger retain actual source storage generation, slot creation and complete encrypted-authority digest; source delete/recreate ABA or later authority mutation cannot authorize an old publication. Candidate issuance atomically retains the exact original `{content,pin}` digest with its record/creation claims. Independently rewriting a coherent archive, pin and committed binding does not replace that ledger issuance. Both IDs stay consumed after lost ledger acknowledgement, failure or restart.

`ciphertextBytes` totals measured current filesystem ciphertext, serialized original SQL custody envelope, and independently authenticated current SQL authority envelope. The SQL quantities are adapter-issued-envelope UTF-8 byte lengths, not original physical JSONB storage bytes. The complete total must fit the declared budget. Later target receipts may increase current SQL authority bytes while immutable original evidence remains unchanged.

## Namespace and qualification limits

New journal records are `wpg_<sha256(activationId)>_attempt`, `wpg_candidate_ledger_v1`, and the candidate `wac_*` archive/pin/binding records. The existing local `wal_*` paired claims, immutable bootstrap/evidence and staging remain in use. All dedicated journal/control/staging/target namespaces require explicit independent accounting in the coordinator/B composition. They stay outside the original source archive with separate recovery/key requirements; `fullWorkspacePortable=false` remains truthful. Wider enterprise SQL/filesystem/external recovery is not supplied by this module.

Focused tests use actual Vault encryption, bootstrap/open/reopen and C-only physical custody, with SQL interfaces explicitly injected as `test-fixture`. They prove protocol ordering and uncertainty behavior. They do not qualify a native PostgreSQL server, competing independent SQL writers, cross-process crash/power loss, public HTTP/Engine composition, September receipt goldens, GUI, live providers, broader namespace restoration or release acceptance. The coordinator owns those joined gates. PGlite remains failed and nondefault.
