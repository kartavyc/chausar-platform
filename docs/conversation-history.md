# Private saved answer history

`ConversationHistoryService.list(context, { limit?, cursor? })` returns only currently readable successful business-context and calculation answers. The default page contains twenty items; the maximum is fifty. Each item contains `id`, `at`, `question`, `kind` and `receiptId`. Order is newest timestamp first, then descending message ID. `nextCursor`, when present, is the last returned message ID. A cursor must still refer to an admitted private answer; a removed, stale, foreign or malformed cursor refuses with `INVALID_HISTORY_CURSOR`.

`get(context, id)` returns `id`, `at`, `question`, `kind` and the exact saved `answer`. Unavailable references refuse with `CONVERSATION_NOT_FOUND`. Caller authorization still uses the existing `ACCESS_REVOKED` guard. List output contains no answer bodies, raw source fields, vault state, unsuccessful messages or profile journal records. Both methods use one synchronous state snapshot. Returned answers are JSON records capped at four MiB; larger records refuse without truncating evidence or substituting an answer.

The Engine supplies mandatory synchronous callbacks for `assertBusinessContextCurrent` and `CalculatorService.receipt`, including its installed connector readiness hooks. These callbacks receive the same explicit read view. `currentReceipt(context, id, view?)` exposes the guarded financial read for the Engine's transaction writer. Saved receipt ownership, current epoch, counted and excluded fact access, explicit branch scope, source access and current managed-domain readiness are checked. Stale receipts and expired conversation, receipt or fact timestamps refuse. Managed empty and excluded scopes remain subject to the existing installed readiness checks. The history does not add a dictionary-current equality rule, reinterpret a historical definition, calculate a replacement number, contact a model or acquire a source.

New financial writes call `createCalculationAnswerRecord(context, question, answer, currentReceipt)` inside the Engine's authorized transaction. It admits only an exact receipt or the successful `{ supported: true, message, receipt }` calculator result, with the receipt's exact explanation. Records bind the author, epoch, timestamp, question, full answer, receipt ID and lineage using `conversationRecordIntegrity(record)`: SHA-256 of canonical JSON excluding only the record's own `integrity`. JSON normalization treats optional undefined receipt fields consistently before and after Vault serialization. Top-level `rowIds` include counted and excluded fact IDs; source roots include the receipt's source IDs and row sources. Existing source deletion and retention cleanup therefore purge the dependent conversation records.

New business writes receive the same full-record integrity binding. Every business read validates its exact current manifest and saved answer against the existing deterministic business renderer, including exact claims, citations, unknowns, scope and nonfinancial receipt binding. The readiness hook delegates to the Engine's current manifest assertion before forwarding the qualified managed scope. The saved body is returned unchanged. Optional model receipt references must still exist for the same author, epoch and context digest and remain within retention.

Compatibility is explicit. An old financial `role: 'user'` conversation with `resultId` can be admitted only when its exact referenced receipt remains private to the current author and epoch and passes all current guards. Those records never saved the original result wrapper, so history reconstructs `{ supported: true, message: receipt.explanation, receipt }` from the persisted receipt. Old unsigned business records can be admitted only through their current manifest and exact deterministic saved-answer validation. Old unsupported messages, missing references, altered text, duplicate message IDs and foreign authority revisions fail closed.

The focused fixtures exercise real local calculator, memory, trust deletion/retention and encrypted Vault reopen paths with authored synthetic values, including a literal billed total of `30000`. A separate controlled host-hook fixture proves expiry delegation for a financial receipt and an empty managed business domain. That hook fixture establishes no connector, vendor, native storage or source qualification. The file adapter remains experimental; the tests perform no provider call, network request or native GUI launch.
