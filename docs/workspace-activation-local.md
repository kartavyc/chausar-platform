# Durable local activation storage

`platform/runtime/workspace-activation-local.ts` supplies the actual encrypted journal, physical target publication and restart inspection portions of `WorkspaceActivationPorts`. It owns no shared Vault, Engine, IPC, manifest or database implementation. Its new `.ports` can be passed to `WorkspaceActivationHost` after the coordinator supplies the required trusted root capabilities.

The focused tests use newly allocated C-drive temporary directories and actual `experimental-file` source and journal Vaults. Their fresh bootstrap is explicitly `test-fixture`: it is encrypted filesystem evidence, not an openable fresh Chausar Vault or usable Engine attachment. Nothing here qualifies native storage, GUI, live providers, migration, complete external namespaces or full-workspace portability. This ordinary application work does not replace the restricted dedicated security review.

## Integration contract

Construct `createWorkspaceActivationLocalPorts(options)` with these root-owned inputs, never renderer/RPC callback data:

| Input | Exact obligation |
| --- | --- |
| `sourceVault` | The currently unlocked actual source Vault, a direct child of the canonical `applicationDirectory`. |
| `journalVault` | A distinct actually unlocked durable control Vault. Its key/credential lifecycle, retention and readiness belong to root. It must remain available alongside source custody for restart inspection. There is no implicit memory ledger or shared source-key export. |
| `source.withSource(context, expectedInventory, work)` | Hold the source Vault snapshot, current owner/access and complete inventory/readiness exclusion through the entire callback, source artifact reads, physical publication, final journal write and readback. Return the actual source Vault State. `assertCompleteOwner` checks all historical sources and rows against CURRENT admission. `assertCurrent` rechecks the retained source and current admission. All assertions finish with `undefined`. The existing local interchange source implements its reviewed business profile; a v2/full custody source requires its own reviewed current inventory join. |
| `candidates.read(context, candidateId)` | Authenticate the actually issued complete candidate, independent pin, creation instance and encrypted committed issuance binding. Caller hashes do not establish provenance. |
| `candidates.withCandidate(context, candidateId, work(reader))` | Hold the issuer's exact candidate exclusion for the ENTIRE callback and supply an already-locked authenticated `reader`. Do not call a reader that reacquires its record lock or the source queue. For the existing local issuer this lock is `.workspace-interchange-control/records/sha256(sourceVault.vaultId + ':' + candidateId).lock`. The module orders locks source -> target -> candidate, matching local preparation. |
| `bootstrap.allocateAuthority(context, target)` | Allocate fresh owner/context/session authority for the reserved workspace. Verify actual current target access and fresh session custody; do not grant historical tokens. The host validates the exact authority shape and disjoint identities. Allocation must not publish a target. |
| `bootstrap.prepare({ stagingDirectory, publication })` | Initialize the EXACT `publication.state` at revision zero with the reserved workspace identity and fresh authority under `stagingDirectory/live`. Close all live handles/writer locks before returning. Return every regular live file as a forward-slash path beginning `live/`, plus the truthful `test-fixture` or `encrypted-local-host` qualification. Only the two immutable files and `live` may be at staging root. No symbolic/hard links, unknown files, external effects, credentials copied from history, or runnable historical jobs/sessions are permitted. |
| `bootstrap.inspect({ targetDirectory, publication })` | Authenticate the actual CURRENT live subtree, fresh workspace/owner/session custody, current permissions/readiness, and valid revision lineage from the immutable initial publication. Complete without mutation, retry, adoption, Engine attachment or an admission return value. Later live revision is distinct from the initial revision-zero snapshot. The root implementation must refuse an unrelated self-consistent live file. |
| `budgets` | Positive `maxFiles`, `maxBytes`, `maxDepth`, at most 4096 files/directories per enumeration, 256 MiB measured bytes and depth 16. Refuse complete operations rather than truncating. |

The module reads the existing source-encrypted `wit_<sha256(targetId)>_reservation` format `chausar.interchange-target-reservation.v1`. Root must issue the candidate against this same newly allocated physical empty target. Existing unrelated directories are never adopted. The target proof's workspace/generation, current access digest, exact encrypted reservation reference and filesystem device/inode/birth-time identity must agree. Publication holds the existing `.workspace-interchange-control/targets/sha256(targetPath).lock`. It uses its own phase-aware lease; the inert issuer's empty-on-exit `withTarget` must not wrap publication.

The current shared `Vault.create` cannot initialize this exact bootstrap: it creates its own workspace identity. `Vault.update` refuses identity changes and increments revision. The missing coordinator port is a reviewed fresh revision-zero Vault initialization from the exact State/authority, followed by current live Vault authentication and Engine/session attachment. This module neither modifies Vault nor implements that requirement using an unlabelled provider stub. Its test bootstrap remains a fixture.

## Durable behavior

The separate journal Vault first reserves BOTH identities in one authenticated `wal_ledger_v1` compare-and-swap write. Its bounded ledger retains at most 4096 distinct activation IDs and source-Vault/candidate-creation tuples. A crash or lost acknowledgement immediately after this write cannot reopen either identity, even before any per-attempt file exists. The module then creates `wal_<sha256(activationId)>_attempt` and `wal_<sha256(sourceVaultId + ':' + candidateCreationId)>_candidate` records. Existing failed, pending, committed or ambiguous identities cannot be reused, even with identical content or a different activation ID. Readback authenticates both the paired ledger reservation and the exact per-candidate claim. Concurrent ledger changes fail the actual encrypted CAS; no in-memory set substitutes for durable admission.

Each attempt also retains two independently encrypted immutable payloads: `_bootstrap` contains the exact ordered initial State, fresh authority and activation binding; `_evidence` contains the complete originally authenticated inert candidate string and independent pin. `JSON.stringify` State key ordering is preserved. Later live writes never rewrite either payload or the activation binding. The target receives exact ciphertext copies named `activation-bootstrap.encrypted.json` and `activation-evidence.encrypted.json`; their decryption still depends on retained journal Vault custody. These are not standalone portable key material.

Staging is a new owned directory below `.workspace-activation-control/staging/attempt_<UUID>`. Exact ciphertext copies are synced and measured before publication. The root prepares a closed fresh live subtree there. The adapter flushes every exact staged regular file itself, including files prepared with `copyFile`, and syncs the staged directory tree. It enumerates and preserves empty live directories as well as all regular files. A `prepared` journal binds the full file/directory list, hashes, byte lengths and physical file generations BEFORE the first target entry is created.

Publication creates directories and files exclusively, using hardlink creates from each exact staged file. An existing path causes refusal rather than overwrite. Every link must retain the staged physical identity; its staging link is removed before readback or live inspection. The source Vault's held writer admission brackets the physical operations, and no guarded journal write nests inside that admission. The target and source fences remain held through complete target verification, sync, final journal commit and readback. Only an exactly verified complete publication gets a `committed` marker.

This is a journaled cross-Vault operation, not an atomic transaction across native databases or a power-loss certification. On Windows the existing directory-sync policy cannot establish hardware-level directory flush guarantees. Interrupted staging and partial targets are retained for explicit root inspection. The module has no automatic cleanup, recovery publication or adoption operation.

## Explicit restart inspection

`host.resolve(context, { activationId })` inspects only. It checks current untainted unrestricted source-owner authority, exact source issuance, durable candidate consumption, authenticated journal payload references, original physical reservation, immutable target file generations and ciphertext, complete top-level layout, and root-authenticated current live custody. It measures actual encrypted bytes and returns the original bootstrap State to the host. Fresh later receipts or revisions cannot substitute for the initial `stateDigest`.

An acknowledged complete final marker, or a final marker whose acknowledgement was lost after its actual write, can resolve `committed` after actual Vault close/reopen. A missing attempt resolves `unknown / ACTIVATION_ATTEMPT_NOT_FOUND`; a prepared/partial attempt resolves `unknown / ACTIVATION_ATTEMPT_UNRESOLVED`. Changed or unauthenticated committed target custody resolves `unknown / ACTIVATION_CUSTODY_UNRESOLVED`. Authority and source admission errors still refuse inspection. Complete files with only a prepared marker remain unknown: the module does not silently finish the transaction. Inspection never creates a marker, consumes a new ID, publishes a missing file or attaches an Engine.

## Namespace and qualification limits

New durable administration lives in the separate journal Vault; it does not add artifacts to the source's strictly classified `workspace-interchange` namespace. The `.workspace-activation-control` staging namespace and separate journal Vault nevertheless require explicit measured root dispositions in any complete v2 backup/current-source profile. The existing v2 local backup profile will refuse unknown application siblings; it cannot silently exclude these controls. Root must declare actual journal key custody and interrupted staging retention, and join these namespaces to current readiness/complete inventory. Do not disguise new records as existing `wic_*` controls or bypass the refusal.

Qualification is persisted in the authenticated prepared/committed journal and uses the weaker candidate/bootstrap classification. Actual local journal ciphertext does not elevate fixture bootstrap to native or usable activation. The module's source, candidate and bootstrap constructor capabilities are still trusted integration obligations; injected fixture ports prove storage mechanics only.

Focused synthetic cases cover exact encrypted original/history, ordered bootstrap, preserved empty live namespaces, later live revisions, actual close/reopen after a lost final acknowledgement, prepared-empty and partial-link unknown outcomes, both IDs consumed after ledger acknowledgement loss, replay with a different activation ID, child-process target/candidate exclusion, current authority/readiness refusal, identical-byte physical target replacement, extra entries, changed immutable ciphertext, and target/admission changes during asynchronous live inspection. Test evidence is retained separately from the source package. It establishes these storage behaviors without claiming the missing exact native Vault bootstrap port.
