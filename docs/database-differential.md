# Native database differential qualification

`node scripts/verify-database-differential.mjs` is a hard qualification gate. It compares independently hand-worked answers against the JavaScript calculator, the production native DuckDB worker, and the native PostgreSQL analytical adapter. It also runs `CalculatorService` with both native verifiers on a real PostgreSQL-backed encrypted `Vault`. Missing dependencies or an unconfigured disposable PostgreSQL database cause a nonzero exit. The runner never converts those conditions into a passing test, a skip, or an injected SQL executor.

The database roles remain explicit: PostgreSQL authority storage contains encrypted snapshots. PostgreSQL analytical verification uses private transactional temporary row projections, which are rolled back. DuckDB analytical verification uses a disposable process and in-memory projection. This does not introduce a persistent normalized claim schema, qualify PGlite, or select a default database.

## Independent answer key

The literal corpus is in `platform/tests/database-fixtures.ts`. Expected figures are written as decimal integer strings and are not generated by the dictionary compiler or either SQL implementation. Successful fixtures assert the entire figure set, so an undefined ratio must actually be absent. Native engines must independently verify each checked receipt; equality between two implementations alone cannot pass the gate.

## Reproducible commands and database guard

Use Node 24.13.1 or newer. The focused JavaScript and guard suite needs no downloaded packages:

```powershell
node --test platform/tests/database-differential.test.ts
```

To run the hard native gate, independently supply the project's pinned `pg` and `@duckdb/node-api` packages and an already provisioned disposable local PostgreSQL database. This runner installs nothing, starts no database process, creates no database, discovers no credentials, and performs no cloud provisioning.

```powershell
$env:CHAUSAR_TEST_DATABASE_DISPOSABLE = '1'
$env:CHAUSAR_TEST_DATABASE_URL = 'postgresql://<fixture-user>:<URL-encoded-fixture-password>@127.0.0.1:<explicit-port>/chausar_test'
node scripts/verify-database-differential.mjs
```

Only literal `127.0.0.1` or `::1`, explicit ports `1024–65535`, nonempty explicit credentials, the exact database name `chausar_test`, and the exact disposable acknowledgement `1` are accepted. URL query and fragment delimiters, including empty `?` and `#`, are refused. Credentials never appear in the report. Before initialization, the runner checks the server's actual database identity, a pinned `public` search path, and the absence of **every public relation**, including views, sequences, and indexes. These are read-only checks. The PostgreSQL analytical adapter confines its temporary projections to `pg_temp`; the authority adapter names its table in `public` explicitly.

The dedicated authority pool bounds server statements to 15 seconds, lock waits to 5 seconds, idle transactions to 15 seconds, and client query waits to 17 seconds. Connected but stalled preflight, CAS or cleanup queries therefore cannot silently wait forever. These are fixture connection settings, not changes to machine-wide or production database configuration.

The snapshot phase uses randomized run-owned slots. Failure cleanup closes owned clients and deletes only those slots. It never drops a table or deletes another run's authority row. The created authority table intentionally remains. Therefore a completed snapshot run makes the pristine guard refuse a second run against that same database: independently reprovision a fresh one-shot fixture database before another qualification. Cleanup failure itself fails the gate. Local encrypted test artifacts are removed only from the runner's generated directory under the system temporary directory.

## PostgreSQL/Vault composition checks

Once both native engines are available, the runner verifies:

1. Exact imported source decimal amounts reconcile independently, and a repeated batch keeps the same import identity without adding claims.
2. `CalculatorService` awaits both native verifiers before persisting each receipt in the composition phase.
3. Exact currency conversion retains its original currency and rational rate in the receipt.
4. A March event learned on 1 April is corrected on 3 April. The immutable first claim stays `10000`; the 2 April view stays `10000`; the 4 April view becomes `12000`; dependent saved answers become stale. The historical clock is explicitly restricted to a labelled demo vault.
5. PostgreSQL contains an encrypted envelope, conceals synthetic plaintext markers, and reports the current snapshot revision.
6. Concurrent slot creation and concurrent revision updates each admit exactly one winner, with the other writer receiving `REVISION_CONFLICT`.
7. Reopening preserves facts, claims, import identity and historical answers; encrypted backup restore into a fresh slot preserves corrected history; deletion removes that restored slot.

These tests establish normal native composition, arithmetic and transactional CAS when they actually execute. They do not establish power-loss durability, operating-system keychain protection, a signed packaged runtime, or crash recovery of the PostgreSQL server itself.
