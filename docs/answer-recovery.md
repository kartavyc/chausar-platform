# Explicit recovery of legacy unpinned answers

`platform/runtime/answer-recovery.ts` prepares a **new calculation** when an existing saved calculation request has no retained `asOf`. It never reconstructs an old cutoff from the receipt, answer creation time, current clock, trial clock, or dictionary publication. Existing private-trial refusal remains valid. The old request, answer and receipt are immutable inputs.

The three pure interfaces are `explainAnswerRecovery`, `prepareAnswerRecovery` and `completeAnswerRecovery`. `assertPreparedAnswerRecoveryCurrent` reconstructs an exact preparation from newly resolved originals before execution. None reads or writes a store, grants permission, validates source readiness, executes a calculation, promotes a trial, or issues an identity. Their SHA-256 pins provide comparison evidence only.

The caller must explicitly declare all four time fields: a known-on ISO timestamp with a time zone, an inclusive event period or `null` for all event dates, a comparison period or `null`, and an aging date or `null`. Change calculations require both periods; aging requires its declared date. Calendar dates reuse `validDate` and `validatePeriod`. The timestamp is normalized to UTC, without changing its selected instant. Original operation, source selection (including omitted or empty selection), branch, customer/order filters and scenario assumption are copied unchanged. The host allocates `newRequestId`; it is lineage identity, **not a calculation parameter or a preexisting saved-answer ID**. CalculatorService will separately issue fresh answer and receipt IDs.

The evidence is an exact three-field answer projection `{id, receiptId, request}` plus its original receipt and current workspace identity. Operation, period, comparison period, branch, requested-source selection, explicit original aging date and scenario assumption must match that receipt. Stale original records may be used as the starting question for a fresh calculation; their stale flags remain unchanged. A retained private-diagnostic restatement and an already pinned request are refused by this particular path. Recovery cannot make an old answer eligible for retrospective trial rebuilding; a successful new answer can later enter ordinary trials under their unchanged checks.

`Engine.privatePromotionImpact` currently includes every request-bearing answer in its retrospective rebuild inventory. Keeping the old unpinned answer therefore still blocks whole-workspace retrospective publication even after a separate pinned answer exists. This helper deliberately does not change that inventory. A separately reviewed public retirement/supersession contract is needed if the product should permit such publication; no deletion, silent timestamp migration, or bypass is supplied here.

## Engine and public renderer integration seam

1. Add a strict public review endpoint accepting only an original answer ID. Under the current Engine context, find exactly one saved answer, resolve exactly one corresponding receipt through the **configured** `services.calculator.receipt(ctx, id)` (including connector receipt guards), then pass the projection and current workspace ID to `explainAnswerRecovery`. Do not accept answer/request/receipt records supplied by the renderer. Enforce current source, branch and epoch rights before disclosing even the recovery explanation.
2. Show the explanation, current published dictionary/currency, and an explicit new-scope form. A changed dictionary may change the meaning of the fresh result; do not promise historical equivalence. Leave the cutoff and aging/comparison choices unselected; do not prefill the historical receipt cutoff or silently choose “now”. Explain that `period: null` means all event dates and require the user to choose it deliberately. Submit exact reviewed source pins, all four new time fields, and `confirmedNewCalculation: true`. Root may require its normal untainted app confirmation. No old trial/promotion capability crosses this seam.
3. The host allocates a new request identity and re-resolves originals and workspace identity. Call `prepareAnswerRecovery`; just before execution re-resolve and call `assertPreparedAnswerRecoveryCurrent`. Apply the existing writer admission and current connector semantic/readiness checks. Run the prepared request through the **normal configured** `CalculatorService.calculate(ctx, plan.request)`. Its original source access, current dictionary, fact-change, consumer/receipt guards and atomic commit checks must remain active. No permissive recovery calculator or readiness bypass is needed.
4. Retrieve the exact newly saved answer by the returned new receipt ID and retrieve that new receipt through the configured current receipt reader. Re-resolve unchanged old request/receipt pins; call `completeAnswerRecovery`. Persist/display this lineage through the host's ordinary revision-checked journal/audit store. Do not inject lineage into an old answer or attach `ReceiptRestatement` to the new receipt. Do not claim lineage publication if its storage operation fails; any already issued new normal answer remains a separate calculation with its original receipt.
5. Read the new answer and lineage through current permissions; retain the historical answer and receipt unchanged. Reopen/public HTTP/renderer acceptance must prove new identity, explicit chosen cutoff, equal old request/receipt bytes, source revocation and changed-evidence refusals. A hash is not a bearer token, freshness grant, or proof the user selected the scope.

The isolated focused tests use synthetic JavaScript StateStore fixtures and the actual CalculatorService. They prove preparation, unchanged original records, exact fresh receipt binding, and ordinary permission/readiness refusal. **Engine/RPC/renderer wiring and durable lineage storage are not implemented in these three files.** They do not qualify a database, connector, native UI or installed application. The original published `706a489` acceptance remains separate.
