# 6H2 Recorded flows (D41)

## What was built

- **Recipe as data** (`platform/runtime/venture/flows/recipe.ts`, shapes in `flow-types.ts`). A recording turns into plain steps: open the page, fill a box, tick a box, press a button, a stop for the owner, a stop before a submit, payment or post. Each step that touches the page names its control by up to six ways to find it (id, form name, test id, aria-label, label words) and a sha256 fingerprint of what the control is (tag, type, name, id, test id, autocomplete, role, form action), never its value. Typed words become blanks (`blank-1`...); the recorded words are kept only as the draft's dry-run samples and are dropped at approval. Checkboxes and choices are fixed values. A press is a stop before a submit by browser.ts's own `sensitiveKind` rule (any button in a form, or a control code cannot read), named pay or post by its words. Password, card and one-time-code fields are a stop for the owner and their value is never kept, even if a page leaked it. A CAPTCHA control, an address with a name or password, a private network address, or a site in the fetch policy's barred list (LinkedIn first) is refused. A recipe has a digest: what the owner approves.
- **Exact replay with no AI** (`flows/replay.ts`). Before every step the control must match exactly one visible element with the recorded fingerprint, or the run stops ("changed page"); a filled box must show exactly the value; a plain press the page now treats as a submit, or one that tried to send, stops; a password stop waits for the owner to type it in the window; a CAPTCHA or check page (browser.ts `pageStop` plus a CAPTCHA frame or widget check) is a hard stop; leaving the recipe's site stops. A dry run ends at the first submit, unpressed.
- **Methods** (`flows/methods.ts`, records in `flows/records.ts`): `venture.flows.list` and `venture.flows.act` with actions record, dry-run, approve, run, continue, repair, stop. One approval, only of the exact version whose dry run passed. A run holds at a submit with a review (each blank's label and value) and a digest of run, recipe, step and values; the owner's tap (`continue` with that digest) goes through the existing exact-approval journal (`journalled`, `connector.write`, new operation `flow-submit`, `gateEffect` at the physical press), then the run goes on to the next stop or the end. If the window closed, or the page changed, before the press, the entry is rejected as not sent, never left unknown. A changed page keeps the controls on the page then (code-collected, never values); `repair` (allowed from the AI tool's MCP channel, marked `proposedBy: 'ai'`) picks one and becomes a new draft version that needs its own dry run and approval; approving it marks the older version replaced. Run values live in memory beside the open window only.
- **Desktop window** (`app/desktop/flow-browser.cjs`): one visible window, page JavaScript allowed, sandboxed, own in-memory partition cleared on close, no permission, download, popup or off-site navigation. Every non-read request (POST, PUT, PATCH, DELETE...) is cancelled unless the engine pressed the approved submit, for ten seconds, to the flow's own site. While recording, a submit is stopped and kept as a stop; a press that tried to send becomes a stop too. Chausar's page work runs in isolated world 1007 with fixed operations; recorded events come back as console lines carrying a random per-window token. Relay in `engine-harness.cjs` (`host-flows`), wiring in `main.cjs` (closes the window when the engine stops), worker port `flows/port.ts` (checks every answer field by field; a recorded event it cannot read is dropped).
- **Fake engine parity** (`app/ui/src/engine/fake-flows.ts`): the fake is not the desktop, so it answers as the engine does off the desktop: an empty list, the same checks, codes and words in the same order (shared `flows/flow-words.ts`), and `FLOW_BROWSER_UNAVAILABLE` where the engine would open the window.

## Deviations and why

- No owner screen yet. No reference UI was drawn for D41 and the package lists engine behaviour; the methods, types and fake are ready for a screen. Open item.
- The run's approval is the owner's tap inside the app through `journalled` (the same pattern as the data-entry desk's forms submit), not a separate Today card.
- The AI repair chooses among controls code collected from the page; it cannot invent a selector. It is not yet listed as a tool in Chausar's MCP toolbox (6B1), only reachable on the MCP channel through the method. Open item.
- Choices (selects) are fixed values, not blanks; only typed text becomes a blank. Editing which values are blanks is not built.
- `flow-browser.cjs` was drafted before its test file; its test was then written and run against it (the red log shows the missing port and relay).

## Open items

- Owner screen for record, test, approve, run, review a stop, repair.
- MCP toolbox entry for repair (and a read of stopped runs) for the AI tool.
- Sites that need signing in first cannot be recorded, because every send is blocked while recording. A saved sign-in partition (like the forms desk's) would solve it.
- The network gate is by HTTP method: a site that changes data with a GET request is not caught by it (the fingerprint and submit rules still apply).
- Filling blanks straight from records (client, order) instead of given values.
