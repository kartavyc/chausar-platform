# 6F4 Outbound webhooks (D33)

## What was built

- `sendToWebhook` (`platform/runtime/venture/build/webhook-handoff.ts`) is now a signed, keyed, retried send with a receipt.
  - **Registered addresses only.** It sends only to the address the owner set with `venture.webhook.set`, held on the secret shelf. The approval digest covers the kind, a digest of the address and the exact text, so a changed address or payload cannot ride an old approval.
  - **Signing.** `venture.webhook.set` now needs a signing secret (16 to 256 printable characters, no spaces) beside the address. It sits on the shelf (`webhook-signing:<kind>`, new `SecretName`), is cleared with the address, and never appears in a view, record, event or the journal.
  - **Headers.** Standard Webhooks layout: `webhook-id`, `webhook-timestamp` (whole seconds) and `webhook-signature: v1,<base64 HMAC-SHA256 of id.timestamp.body>`. `idempotency-key` carries the same id.
  - **Idempotency.** The id is the journal's claim key (`<entry>.once`), the same on every try.
  - **Timeout.** 15 s per try through the network guard (`guardedFetch`, no redirects).
  - **Limited retries.** At most `WEBHOOK_ATTEMPTS = 3` tries, and only when the earlier try is known not to have run: a failed name lookup (nothing left the computer) or a 429 (Retry-After honoured up to 10 s). Waits are 1 s, then 3 s.
  - **Unknown outcomes.** A timeout, a lost connection, a 5xx or any other error after sending is `outcome_unknown` at once and is never retried. The journal then refuses the same subject.
  - **Receipt.** The journal entry (`connector.write` / `webhook-send`) is the receipt. Its final line names the status, the delivery id and the try number.
- New method `venture.webhook.send { kind, subject, payload, digest? }` (approve, app only).
  - Without `digest` it answers the preview: the exact canonical text, the host and the digest to approve. Nothing is proposed or sent.
  - With `digest` it sends exactly that text. A mismatch gives `APPROVAL_STALE`, nothing leaves and nothing is journalled.
  - The answer (`WebhookSendView`) is the receipt: state, status, deliveryId, attempts and entryId.
  - Registered in contracts (method list, owner, app-only list, permission, payload and result types), method hints, the desktop IPC allowlist (`.cjs` and `.d.cts`), the engine switch, the UI types and the fake engine.
- Connections, "Your n8n or Make": a "Signing secret" field (outside any form, autocomplete off, cleared in a finally) and a quiet "Make one" button. The button fills a random 32-byte base64url secret in the page so the owner can copy it into their n8n or Make check. Save stays off until both fields are filled. The form is folded at rest, so at-rest words do not change.
- Fake engine: same secret check, in the same order as the engine; `webhook.send` with preview and send, `APPROVAL_STALE`, `WEBHOOK_NOT_SET` and `JOURNAL_ALREADY_DECIDED`.

- Passed (`results/w6-6F4-live.json`, script `results/w6-6F4-live.ts`). Setup:
  - The real engine handlers ran on a real HTTP socket, aimed at a receiver started on 127.0.0.1 and stopped at the end.
  - Only the final socket was pointed at the receiver: the production guard refuses loopback and plain http by design.
  - Registration, signing, journal and receipt all ran as production code.
- Results:
  - Two requests (the test item and one synthetic item).
  - All signatures verified, and `webhook-id` equalled `idempotency-key`.
  - The delivery id matched the receipt, and the body was byte for byte the preview text.
  - The repeat was refused `JOURNAL_ALREADY_DECIDED`.
  - The secret is in no record.

## Deviations

- Zapier is not added. D33 names it, but a new `WebhookKind` changes the connector catalogue and three shared connector lists that other helpers are editing now. n8n and Make are covered. Zapier is one kind plus one catalogue row later.
- No Today card. Like Razorpay (6D3), a send is approved by the owner pressing Send on the exact preview in the app (the journal's `journalled` path). Today has no generic card for described journal entries.
- Only the test item has a UI caller. `venture.webhook.send` is the wired engine path for playbooks, the agent and later screens. The catalogue rows keep their honest `fixture-tested` label ("In this build that is the test item"), because no real n8n or Make has received an item.
- The secret uses its raw UTF-8 bytes as the HMAC key, not the `whsec_` base64 form of the Standard Webhooks libraries. A receiver's check must hash with the plain secret text.
