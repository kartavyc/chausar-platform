# 6F6 Telegram alerts (D35), live-tested

## What was built

- **The owner's own bot, in protected storage.** `venture.notify.telegram` (approve, app only; new file `platform/runtime/venture/notify/telegram.ts`): `{ bot: { token, chatId } }` saves the token and chat id together under the credential name `alerts:telegram` through the host's credential port (the same port as model keys and Razorpay; the name is added to `credential-contract.cjs`). `{ bot: null }` deletes them. The business file keeps only `telegram: { details, savedAt }` on the notification settings record, never the token or chat id (tested by scanning the whole store).
- **Counts by default, details opt-in.** Each alert outside the app sends one message: `Chausar: 3 things wait for you. Open the app to decide.` `{ details: true }` adds the titles of the items that alert counted, one per line (control characters and links stripped, 80 characters each, 10 at most). The line says plainly that titles can name clients.
- **Approvals stay in the app.** The message has no link, no button and no `reply_markup`; nothing in Telegram can approve. Settings and the test are app-only, so a phone context is refused (`APP_APPROVAL_REQUIRED`).
- **Uses the existing alert path.** `notify/index.ts notifyRefresh` already sends each due alert to web push and the relay after the centre's commit; Telegram is a third delivery there (`deliverTelegram(deps, ctx, count, at)`), with the same pacing, quiet hours, pause, "owner watching" rule and give-up after three tries. `channelsOn` counts a set bot as a channel on the desktop, so alerts are planned even with the tray off.
- **Journal.** Each send is its own journal entry under the owner's standing setting, reusing the existing `notify.relay` action (subject `notify-relay:telegram-<alert>:<attempt>`, target `api.telegram.org`), as 6D3 reused `connector.write`. The digest is made from the host, the alert id, the attempt and the text; the token and chat id are never in the entry. A 4xx is not retried and shows Telegram's own words (401/404 say the token was refused); no answer or a 5xx/429 is tried once more as a new entry.
- **Network.** Through `guardedFetch`: https, public address checked and pinned, redirects refused, 8 s timeout, 64 KiB answer cap.
- **Test alert.** `{ test: true }` sends the current count only (open notification items), even with details on.
- **Hosted.** Refused with `TIER_UNAVAILABLE`: "The hosted app does not talk to Telegram. Telegram alerts come from the desktop app."
- **UI.** Business > Notifications, "How alerts reach you", a closed fold **Telegram alerts** (`app/ui/src/places/business/PhoneReach.tsx`): token (password field, cleared after save), chat id, Save bot, Send a test alert, Remove bot, "Add titles to alerts". The fold asks the engine only once opened. Words at rest stay within the 200 budget (the relay hint was shortened by five words to make room for the two fold titles).
- **Fake engine** (`fake-notify.ts`): same codes, words, checks and order; sends nothing.
- **Guide.** Bot setup, how to find the chat id and what details mean are in `docs/venture/phone-access.md`.

## Deviations and why

- No new journal action id: a Telegram send is a `notify.relay` entry with its own subject prefix, so the existing standing-alert rule, journal list filter and simulation apply unchanged.
- The chat id is typed by the owner (the guide shows how to read it from `getUpdates`). Finding it automatically was left out to keep Chausar from reading the bot's updates.
