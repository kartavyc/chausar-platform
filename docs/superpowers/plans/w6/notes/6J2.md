# 6J2 Feedback (D47)

Live-checked. On 2 November 2026 one synthetic milestone went to the founder's PostHog project and one synthetic test error went to the founder's Sentry project, both through the real handlers. Both answered HTTP 200.

## What was built

Everything is off by default. With no record, reports are off, and nothing ever leaves on its own.

**Engine** (`platform/runtime/venture/core/feedback.ts`, with the browser-safe parts in `core/feedback-core.ts`). Six methods, owned by `core`:
- `venture.feedback.get` (read). Returns:
  - the privacy notice and its digest
  - the consent, with usage reports and crash reports each on or off
  - whether this build has report keys (honest line: "Reports are not set up in this build, so nothing can be sent.")
  - the random report id (`rep_` + 16 hex)
  - the exact preview
  - the open question, the last send and the last deletion request
- `venture.feedback.consent` (approve, app only). `{ digest, usage, crashes }` agrees by the notice's digest; a changed notice gives `APPROVAL_STALE`. `{ withdraw: true }` turns both off and erases what was waiting. Turning one kind off drops only that kind.
- `venture.feedback.send` (approve, app only). `{ digest }` must equal the preview's digest. PostHog gets the preview's events as one `POST /batch/`. Sentry gets each crash as its own envelope (`POST /api/<project>/envelope/`). Only the services' own keys are added on the way: PostHog's project key goes in the body, Sentry's public key in `X-Sentry-Auth`. Whatever a service did not accept waits for the next send, and the line says which service refused.
- `venture.feedback.answer` (prepare, app only). The open question takes `easy`, `okay`, `hard` or `skip`. Free text is never accepted.
- `venture.feedback.crash` (prepare, app only). The window or the desktop shell notes a crash. It is scrubbed once and kept only while crash reports are on, up to 20.
- `venture.feedback.delete` (approve, app only). This is "Delete my reports". See Deletion below.

**What a report holds.** `telemetry.ts` gains `REPORT_EVENTS` and `reportProperties`, built on the existing allowlist rule: a count, a flag, a fixed word or a range, and nothing that can hold words a person wrote. There are four events:
- `chausar_report`. Holds:
  - app version, channel and OS word
  - the furthest milestone and weeks since start
  - AI route: `codex`, `claude-code`, `api-key` or `none`
  - 30-day counts: runs started, finished, failed and stopped; AI calls done and failed; drafts accepted, edited and rejected; cards denied
  - invoiced and received this month, as ranges from `none` up to `200k-plus`, plus the currency code
- `chausar_milestone`, each one sent once. Drop-off is the funnel over these: `business_started`, `plan_accepted`, `ai_connected`, `first_client`, `first_order`, `first_job_done`, `first_invoice`, `first_payment`.
- `chausar_answer`
- `chausar_deletion_requested`

Earnings are summed by code from the money module's own plans (`invoicedPlan`, `receivedPlan`, BigInt minor units). Only the range leaves. Each event carries `$geoip_disable: true`. The report id is PostHog's `distinct_id`, never a property.

**Crash scrubbing** (`scrubCrashText` and `scrubStack`). These are taken out of crash text:
- quoted text
- URLs and emails
- any word with a slash or backslash, which covers every path
- phone numbers and runs of 4 or more digits
- words of 6 or more characters that mix letters and digits (ids and keys)
- capitalised or non-English words, unless they are on a short list of common error words (names)

The result is capped at 300 characters. Stack frames keep only a code file's own name (`.ts`, `.tsx`, `.js`, `.cjs`, `.mjs`) with its line and column. Other frames are dropped. The Sentry event has `user.id` set to the report id, no server name, no IP and no timestamp, so the preview is exactly what is sent.

**Questions after milestones.** One question at a time follows `ai_connected`, `first_job_done`, `first_invoice` and `first_payment`, and only while usage reports are on. Each is asked once.

**App.**
- Business > Reports (`places/business/ReportsView.tsx`, at `#/business/reports`) is listed in the business menu and, like Settled chats, joins the page row only while it is the page. It shows the notice, the two ticks, Turn on reports or Save choices and Turn reports off, "What Send report sends" with the exact JSON (quoted content), Send report, the report id, and Delete my reports, which asks twice.
- Today shows `parts/FeedbackQuestion.tsx` only when the engine has a question open, so Today at rest is unchanged.
- `shell/crash-relay.ts` passes uncaught window errors and rejections to the engine, at most 5 a session. It never throws.
- All strings are in `text/en/feedback.json`.

**Desktop.** `app/desktop/feedback-keys.cjs` hands the worker the `CHAUSAR_FEEDBACK_*` variables. It reads the shell's own environment first, then a packaged build's `resources/feedback.json`. `main.cjs` notes a window that stopped (`render-process-gone`) as a desktop crash. `host-env.ts` `feedbackEnv` reads the variables into `deps.feedback`, accepting https only. `host.ts` passes it on and notes a non-Chausar engine error as a crash.

**Fake engine** (`engine/fake-feedback.ts`). It uses the same core file, codes, order and words. The rehearsal has no report keys, like a build without them, so Send report gives `FEEDBACK_NOT_SET_UP`. Its report is sample data shaped like the engine's: started, plan, AI, nothing earned.

## For 6J4 (the beta guide): sending a report

Exact path: open the business menu (the business name at the top of the rail), then **Reports**. The page is titled "Reports".
1. Read the "Privacy notice".
2. Under "What to report", tick **Usage reports** ("Counts, steps reached and earnings as a range."), **Crash reports** ("Crash details with names and paths taken out."), or both.
3. Press **Turn on reports**.
4. "What Send report sends" now shows every event, exactly as it will go, with the line "Only each service's own key is added on the way."
5. Press **Send report**. The line at the top says what PostHog and Sentry accepted.

To stop, press **Turn reports off**. To remove them, press **Delete my reports**, then **Yes, delete my reports**.

After some milestones, Today shows "A short question" with **Easy**, **Okay**, **Hard** and **Not now**.

## Desktop and hosted

The engine code is the same on both. Desktop gets its keys from the shell (environment or `feedback.json`), notes window crashes, and reports `channel: desktop` with the OS word. Hosted shows the same opt-in, preview and Send report, with `channel: hosted-web`. But `hosted/app.ts` composes no report keys today, so hosted says "Reports are not set up in this build". It has no window-crash relay from Electron, though the browser crash relay and engine error notes work. Reports are kept per business vault, so each business has its own report id.

## How keys reach a build (proposal, nothing hard-coded)

The founder sets three variables when building: `CHAUSAR_FEEDBACK_POSTHOG_KEY`, `CHAUSAR_FEEDBACK_POSTHOG_HOST` and `CHAUSAR_FEEDBACK_SENTRY_DSN`. `scripts/desktop-package.mjs` writes them into `resources/feedback.json` as `{ posthogKey, posthogHost, sentryDsn }`, with `extraResources` in the builder config. The file is git-ignored and never committed. A build without them has no keys, and the app says so.

Only write-only keys ship: PostHog's project key and Sentry's DSN, both made for client apps. No personal or admin token ever does. A developer just exports the variables. `desktop-package.mjs` belongs to 6J1, so I did not edit it. That is an open item.

## Deletion, honestly

PostHog's person and event deletion needs a personal API key, and Sentry's event and issue deletion needs an auth token with admin scope. The app must never carry either. So "Delete my reports" does this:
- drops everything waiting
- turns reports off
- forgets the id
- if anything was ever sent, sends one `chausar_deletion_requested` event under that id and says: "Asked the Chausar team to delete reports sent under rep_… In PostHog and Sentry only the project owner can delete, so the team does it by hand. Until then they stay, under this random id and no name."

If nothing was sent: "Nothing had left this computer." The founder's routine:
1. In PostHog, filter on `chausar_deletion_requested` and delete that person with their events.
2. In Sentry, search `user.id:<id>` and delete those issues.
3. Recommended: turn on PostHog "Discard client IP data" and Sentry "Prevent storing of IP addresses".

## Deviations

- **The report is a snapshot.** It is worked out from records each time the preview is shown, so no milestone hooks had to go into other packages' files. Drop-off is PostHog's funnel over the milestone events. The live batch carried the report snapshot next to the one milestone.
- **Fake test after code.** The fake test was written right after its code and passed on its first run.
- **Shared tests updated.** The pinned method counts are now 383 and 363 hosted, since 6J2 is the only Batch 10 package adding methods. `app/ui/tests/places/business.test.tsx` menu expectations now include Settled chats (a failure left from 6G1) and Reports.
- **A new place without a budget.** Business > Reports is not in `words.json`. At rest it shows the notice and about 170 words. The integrator or founder sets its budget.
