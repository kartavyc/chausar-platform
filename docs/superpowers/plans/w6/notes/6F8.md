# 6F8 People search (D37), fixture-tested, needs your key

## What was built

- **Services** (`people/people-data.ts`, `people-types.ts`, `services.ts`): Happenstance for the owner's own network and their friends' networks; Probe42 for Indian company records from the MCA; Tofler listed as **planned** ("Waits on Tofler publishing API documentation Chausar can read", meanwhile the MCA website or tofler.in). Happenstance and Probe42 say "fixture-tested, needs your key". Apollo is not added (D37: later).
- **Keys:** `venture.people.services` reads the view; `{ service, key }` saves the owner's key in protected storage (`people:happenstance`, `people:probe42`, added to `models/credential-contract.cjs`; no Tofler name while it is planned); `key: null` removes it. The business file keeps the last four characters and the date (`VentureRecord.peopleKeys`). App only.
- **Lookups:** `venture.people.lookup { service, query, clientId? }` answers the exact lookup to approve and sends nothing. Happenstance shows the lead desk's dated credit price (2 credits, checked 27 October 2026, refused when older than 90 days). Adding the quote's `digest` runs it once through the action journal (`connector.write`, operations `happenstance-search` and the new `probe42-lookup`), bound to the key's digest; a 4xx is "not sent", a 5xx or no answer is an unknown outcome the owner checks; nothing is retried. The digest includes the owner's local day, so an exact repeat the same day is refused and the next day it may run again. `{ service: 'happenstance', searchId }` reads a search's results (no credits, no approval).
- **Requests** (from the public docs): Happenstance `POST https://api.happenstance.ai/v1/search` `{ text, include_my_connections: true, include_friends_connections: true }` with a Bearer key, then `GET /v1/search/{id}` (RUNNING, COMPLETED, FAILED; results with name, current title and company, summary, socials.happenstance_url, mutuals). Probe42 `GET https://api.probe42.in/probe_pro/companies/{CIN}/base-details` (or `llps/{LLPIN}`) with `x-api-key` and `x-api-version: 1.3`, or `GET /probe_pro/entities?filters={"nameStartsWith":...}&limit=10` for a name. All through the network guard as Chausar.
- **Client permission:** a lookup with a `clientId` needs that client's recorded permission (`requireClientAiConsent`), bound into the quote and checked again right before the send; withdrawal in between refuses it.
- **Nothing from LinkedIn:** a LinkedIn address (or lnkd.in) as a lookup is `PEOPLE_LINKEDIN_REFUSED`; LinkedIn links in Happenstance answers are dropped and never opened; only happenstance.ai profile links are kept.
- **Minimum data:** answers are not stored. People keep name, title, company, a 300-character summary, a mutual count and the Happenstance link; a person whose words are aimed at the AI is held. Companies keep name, CIN or LLPIN, status, date formed, kind and state; directors, email, address lines and money fields are dropped. Card, bank, Aadhaar and one-time code numbers are refused in a lookup.
- **What the business needs (6C7):** the Happenstance and Probe42 rows now say "Fixture-tested, needs your own ... key: add it under Connections, More ways to connect" instead of waiting on Chausar's connector. They stay `planned` in that list until a real run.
- **UI:** "People search" inside the closed "More ways to connect" fold (`places/connections/PeopleSearch.tsx`), labelled fixture-tested in words (KitConnect now accepts that word label beside the four connector labels); key fields are password fields cleared after each save; "Show the exact lookup" then "Approve and look up".
- **Fake engine:** `engine/fake-web-people.ts`, using the engine's own pure checks, view and quote digest; asks no service (labelled sample records).
- **MCP:** neither Happenstance's OpenAPI nor Probe42's portal mentions an MCP server, so both use REST through the network guard; nothing was registered with the 6F1 client.

## Deviations and why

- Tofler is listed as planned rather than built: its API documentation is not public. Probe42 covers Indian company records meanwhile.
- One quote per lookup per day, so a repeat the same day is never charged twice and a later repeat is possible.
- The lookup UI lives in Connections; a lookup started from a client's sheet (passing `clientId`) is supported by the engine but has no button there yet.
