# 5K2 Zoho provider adapter handoff

- Scope: provider-local implementation only. This is not K2 completion, a connector label change or a live-account certification. Root owns public routes, credential vault, stored approval binding, UI, fake, journal and final package review.
- Ownership: `platform/runtime/adapters/accounting/zoho-write.ts`, new `zoho-write-payload.ts` and browser-safe `zoho-write-types.ts`, `platform/tests/accounting-zoho-write.test.ts`, this note. No shared implementation files changed. Root separately owns posting foundation; independent reviewer regressions remain in `venture-books-posting-review.test.ts`.
- API: `createZohoWriteAdapter({dataCenter,organizationId,accessToken,revision}, net)` returns `connectionIdentity`, `readExisting`, `prepareDraft(row,mapping)`, `sendDraft(prepared,beforeSend)`, `issue(existing,beforeSend)`. Revision must be engine-generated whenever stored credentials/config change. Identity binds provider, data centre, organization and revision; no token enters the prepared object or digest.
- `ZohoDraftMapping` is exact: customerId, placeOfSupply, gstTreatment (business_gst/business_none/consumer), gstNo (string/null), taxSpecification (intra/inter), lineMode (`aggregate-non-inventory`), ordered lines of itemId/taxId/taxKind (`tax`/`tax_group`). The owner/bookkeeper explicitly chooses the GST applicability; this adapter does not infer a tax jurisdiction or legal exemption.
- `ZohoPreparedDraft` contains exact decision and mapping, their digests, connectionIdentity, method/path/query/body, evidenceDigest, lineMode and whole-object digest. Root must persist and seal this entire object in the displayed dry run. Fresh provider evidence is re-read from the saved decision/mapping after restart, without an ephemeral prepared-object registry.
- Preparations fetch the exact customer, items, tax definitions/group members and original invoice where applicable. An explicit different organization in provider evidence is refused. Active INR customer identity, GST treatment/place, SKU, non-inventory item type, HSN/SAC and selected tax preference must agree.
- Supported India taxes: configured simple IGST for inter-state mapping, equal configured CGST+SGST group for intra-state mapping, or explicit provider nil/zero tax. Every component is computed in BigInt from the fetched percentage. Fractional-paise components are refused rather than guessing Zoho rounding. No US exemption fields or invented rates are sent.
- Amounts become literal JSON decimal numbers by dividing BigInt paise into whole/fraction digits; no money passes through Number. Invoice body uses one explicitly labelled aggregate unit per non-inventory line and the exact fitted rate, `is_inclusive_tax:false`, `send:false`; query also pins `send=false`.
- Credit-note creation uses `is_draft:true`, the exact original invoice query and per-line invoice_id/invoice_item_id. It requires the original to match customer, reference, complete amounts, taxes, place, exact quantity 1 and zero discounts. Duplicate original line identities are refused. The documented create schema omits a line rate while its common/update schema includes it, so no unsupported rate is invented for create; the verified original invoice line supplies it.
- Unsupported cases use BOOKS_MAPPING_UNSUPPORTED with the reviewed manual Zoho route: any nonzero shipping (the checked credit-note create schema has no shipping field and the invoice schema does not establish India shipping-tax semantics), inventory quantities, partial/fractional or discounted original lines, overseas/reverse-charge/cess/compound/exempt mappings and evidence gaps. Root must show these constraints beside the owner connection and in the PR.
- `sendDraft` checks the stored seal and rebuilds current mapping evidence before sending the exact approved bytes. The synchronous beforeSend callback is called by the pinned transport after async lookup and evidence checks; no redirect or retry is performed. Revocation at that boundary makes zero POSTs.
- `issue` re-reads the exact identified draft and checks its evidence before POSTing only `invoices/{id}/status/sent` or `creditnotes/{id}/status/open`. It never emails, applies credits or pays a refund. Root still requires post-send readback and durable unknown-outcome handling.
- Credit-note lookup uses the documented `search_text` filter, scans every bounded page and ignores unrelated search matches while rejecting duplicate exact references. Readback retains actual date, document kind and original invoice identity; absent identity cannot confirm a send. Credit notes without a shipping field have zero inferred only when line amounts plus tax reconcile exactly to the returned total.
