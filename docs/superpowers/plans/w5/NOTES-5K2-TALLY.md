# 5K2 Tally provider handoff

- Scope: provider-local draft implementation and refusal boundaries only. This does not complete 5K2 or qualify a live Tally installation. No real Tally capture was available. Root owns connector labels, saved consent, public routes, journal, UI/fake, exact approval sealing and readback outcomes.
- Ownership: `platform/runtime/adapters/accounting/tally-write.ts`, `tally-write-xml.ts`, browser-safe `tally-write-types.ts`, `platform/tests/accounting-tally-write.test.ts`, this note. Existing Tally XML parser is imported without edits. No shared implementation edits, git mutations or root lockfile edits.
- API: `createTallyWriteAdapter(config, runtime)` returns `connectionIdentity`, `readExisting`, `prepareDraft(row,mapping)`, `sendDraft(prepared,beforeSend)`, `issue(existing,beforeSend)`. Config requires exact company name and GUID, port 1024..65535, engine-generated revision, enabled true, explicitly reviewed INR base currency and its actual Tally currency name. Runtime host must be engine-supplied desktop. Runtime sender injection is a test boundary, not an owner field.
- Connection is always numeric IPv4 loopback `127.0.0.1`, POST `/`, no arbitrary URL, DNS, proxy, redirect or retry. Actual transport has an absolute 15-second deadline and 4 MiB response/request limits. Every read requires the enabled saved connector. `beforeSend` runs synchronously immediately before the one physical import transport, after all awaited evidence checks. A thrown approval guard makes no write. Root must recheck current saved consent/revision in that guard.
- `TallyDraftMapping` contains explicit party ledger name/GUID, ordered source itemId to sales ledger name/GUID mappings, lineMode accounting-ledger-amounts, taxTreatment not-applicable, and optionalTemplateXml. Source itemId must equal the actual mapped ledger GUID. No item, party, ledger, master or opening balance is created implicitly.
- `TallyPreparedDraft` stores exact decision/mapping and digests, connectionIdentity, evidenceDigest, exact rebuilt XML body, method POST, lineMode and whole-object digest. It is secret-free and restart-safe. Root must persist and display the exact body/mapping with the dry run and bind the whole prepared object to approval. Send reconstructs evidence from the stored mapping and requires identical fresh prepared digest.
- Evidence-bound scope is an accounting Sales voucher, no inventory, with positive sales ledger amounts and exactly one balancing negative party ledger amount. Tax and shipping must both be exactly zero, explicitly not applicable. Live party must be under Sundry Debtors and sales under Sales Accounts; base currency must match, billwise/cost centre modes must be off, GSTApplicability must be Not Applicable. Unsupported schemes, refunds, allocations, tax, shipping and master/setup writes stay manual. No legal applicability is inferred.
- Owner source XML is untrusted. A bounded existing parser rejects DTD/entity and malformed structures. The new strict profile allows one optional Sales voucher or a constrained single-voucher import wrapper, rejects extra tags/attributes, duplicate fields, Alter/Delete actions, inventory/statutory/embedded extensions, regular vouchers and contradictory signs. It checks balanced exact BigInt paise and never replays opaque XML. The captured MASTERID/GUID/date/amounts/party/ledgers must match the current live voucher in the selected verified company. New XML is rebuilt from validated values and sets ISOPTIONAL Yes; source voucher master identity is not reused.
- Current live voucher reads deliberately fetch complete native objects. Selecting only the accepted fields could conceal unsupported inventory/statutory behavior. Consequently ordinary exports containing extra native metadata may be refused. Do not strip fields or fabricate a capture to enable them. The connector stays planned for an unqualified installation, with manual entry meanwhile, until a real company/release export is reviewed and its exact safe profile is qualified. Synthetic tests establish parser/transport boundaries only, not real Tally compatibility.
- Existing lookup is one bounded collection filtered by Chausar reference, with company identity checked before and after. Missing/failed/partial/oversized evidence fails BOOKS_READ_FAILED. Duplicate references, master IDs or GUIDs and invoice evidence for refund references are refused. Readback reconstructs exact financial digest from current ledger GUIDs and amounts, retains actual date and optional/regular status, and identifies invoice kind with originalId null. Root must still re-read after the write and treat missing or mismatched readback as outcome unknown.
- Automatic issue is deliberately absent: `issue` always refuses BOOKS_ISSUE_MANUAL without reads, callback or writes. Official help documents opening an optional voucher, pressing Ctrl+L to make it Regular, then saving. Automatic conversion requires a separate real capture and qualification; no guessed Alter request is sent. Root must show the manual path and must not advertise automatic Tally issue. Zoho supplies the separate tested issue path for its supported documents.
