## Adapter source lease

`PostgresSnapshotAdapter.withLease<T>(work: (lease: PostgresSnapshotLease) => Promise<T>): Promise<T>` retains one connected client, BEGIN, `pg_advisory_xact_lock(hashtext('chausar-vault:<slot>'))` and authority row FOR UPDATE through the awaited callback. Adapter `load`, `commit` and nested `withLease` on THAT adapter use the same active transaction through AsyncLocalStorage. No nested BEGIN/COMMIT or second-connection lock reacquisition. Leases refuse after release.

Lease exports: readonly `slot`, readonly `active`; `query(sql, values?)`; `load()`; `commit(envelope, expectedRevision)`; `authority(): Promise<PostgresAuthorityIdentity|null>`; `assertCurrent(expected: PostgresAuthorityIdentity)`. Authority identity is `{creationId, vaultId, revision, envelopeDigest}`. `normalizePostgresEnvelope` and `postgresEnvelopeDigest` reconstruct/hash the complete known v1 envelope order without changing any values or decrypted State. Unknown outer/wrapper/ciphertext fields refuse.

The caller holds `vault.snapshot` FIRST, then the SQL lease, with held owner/readiness/filesystem guards around its operation; reversing these locks can deadlock a previously queued Vault mutation waiting for SQL custody. Capture can call `vault.captureEncryptedCustody` while the adapter lease is active. Close adapters/pools only after callbacks release. The source pin must retain `creationId`, not just revision and Vault ID, to distinguish delete/recreate ABA.

## Storage/target custody

`new WorkspacePostgresCustody({adapter: PostgresSnapshotAdapter, targetDirectory?: string})` is a trusted constructor-only capability. No RPC-supplied pool, adapter, credentials or path. `withSource<T>(work: (source: PostgresSourceCustodyLease) => Promise<T>)` supplies readonly storage+authority identities, the native lease, `assertCurrent()` and final exact assertion. `storageIdentity()` returns actual SQL `{storageId,databaseOid,database,serverAddress,serverPort,slot}`; storageId is a durable database generation UUID and authority creationId is a per-slot incarnation.

Target methods require an existing canonical physical directory supplied by root. `reserve({operationId,creationId})` checks both actual absent authority SQL row and actual empty directory, then persists its exact physical generation. It returns `PostgresTargetReservation` containing `{format:'chausar.postgres-target-reservation.v1',storage,operationId,creationId,target:{directory,physical:{dev,ino,birthtimeNs}}}`. Target process/filesystem exclusion must remain held by the activation lane through all awaited publication operations; this module checks physical boundaries, not continuous exclusion of hostile filesystem writers.

`prepare({reservation,envelope})` requires fresh revision 0 ciphertext and returns `PostgresPublicationProof` = reservation + `{vaultId,revision,envelopeDigest}`. The ciphertext remains only in the separate custody row, not ordinary authority. `publish(proof)` atomically INSERTs the authority with the reserved creationId and marks committed, after exact proof/absence/generation checks. No overwrite or retry/adoption. Root authenticates and durably publishes filesystem evidence before invoking SQL publication, and retains committed/uncertain state on lost acknowledgement.

`createPreparedAdapter(reservationOrProof): EncryptedSnapshotAdapter` is a constructor-only fresh-bootstrap capability for `Vault.createBootstrap({directory: <separate FS staging directory>, storage: custody.createPreparedAdapter(reservation), ...})`. Its load/commit exposes only the exact reserved/prepared custody envelope; creation produces the preparation proof available from `inspect(reservation)`. It creates no ordinary authority and permits no updates. Its delete performs exact prepared rollback with its retained original proof; it never calls legacy unconditional deletion. Keep the reserved physical target empty during bootstrap, stage its files elsewhere, authenticate/publish filesystem material, then call `publish(proof)`. After publication open a fresh normal `PostgresSnapshotAdapter` against the target slot. This removes the existing Vault bootstrap-cleanup TOCTOU from the target join without changing Vault.

Publish files into the retained reserved directory; do not replace it with the staging directory by rename, because replacement changes the physical generation. Prepared bootstrap readback may reconcile a lost preparation acknowledgement only against its locally submitted exact proof; arbitrary discovered ciphertext cannot be adopted. An acknowledged exact bootstrap cleanup exposes null on that same prepared adapter while ordinary adapters still refuse its durable rollback tombstone.

`inspect(reservationOrProof)` returns `{status:'absent'|'reserved'|'prepared'|'committed'|'rolled-back'|'unknown', ...}` plus exact retained reservation/proof/ciphertext when authenticated. A committed authority advanced by ordinary admitted writes retains exact original encrypted publication evidence and current authority identity; replacement/corruption is unknown. SQL errors surface and must be treated as unknown by the host. Inspection never publishes, deletes or adopts.

Root durably journals the locally chosen operationId/creationId BEFORE reserve. If the reservation SQL commit loses acknowledgement before returning the full reservation, `inspectOperation({operationId,creationId})` performs explicit read-only recovery against the constructor-installed slot/database/directory and exact persisted operation/creation ownership. It returns the same inspection states and retained evidence, without reserving again or publishing/deleting/adopting. A different occupant/operation/generation is unknown. Hosts must authenticate their own journal and filesystem evidence as well; this inspection is SQL custody, not cross-store completion.

`rollbackPrepared(reservationOrProof)` only tombstones reserved/prepared custody after exact identity/digest and authority absence checks; prepared phase requires the full original proof, not only its reservation. `rollbackExactPublication(proof)` is an explicit trusted rollback of a KNOWN exact committed revision-0 authority; it compares operation ID, creation ID, storage/slot, Vault ID, revision, digest AND SQL JSONB envelope equality in a conditional DELETE. Changed/replaced authority refuses. It never removes filesystem material. Never call it automatically after lost acknowledgement/possible commit; use inspection and retain material instead. No target rollback calls legacy `adapter.delete()`.

Schema initialized by adapter: authority gains stable `creation_id TEXT NOT NULL DEFAULT gen_random_uuid()::text`. Storage table `public.chausar_workspace_postgres_storage(id TEXT PRIMARY KEY CHECK(id='current'),storage_id TEXT NOT NULL)` contains exactly the current generation. Custody table `public.chausar_workspace_postgres_custody(slot TEXT PRIMARY KEY,operation_id TEXT NOT NULL UNIQUE,creation_id TEXT NOT NULL UNIQUE,storage_id TEXT NOT NULL,phase TEXT NOT NULL CHECK(phase IN ('reserved','prepared','committed','rolled-back')),target_identity JSONB NOT NULL,vault_id TEXT,revision BIGINT,envelope_digest TEXT,envelope JSONB,updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP)`.

Ordinary adapter loads/commits refuse reserved/prepared/rolled-back slots. Committed slots require exact custody creationId and Vault ID; subsequent ordinary revision advances are allowed. A missing/replaced committed authority refuses. The new tables must be catalogued by B's actual SQL namespace enumeration as storage control metadata, not silently counted as exported business State.

## Frozen Vault cleanup contract repair

Repair base is the clean local joined commit `cc6295818b29dbfe703d520e883839458d236ce9`, including shared constructor/Vault contract `5eba1f017190466ba3dea5e9e8aeb2feb89b305f`. Shared Engine/Vault files and the two originally failing bootstrap tests are unchanged.

Ordinary cleanup compares the full normalized encrypted envelope, Vault ID, revision and an internally retained original creation identity in one slot transaction. Ownership is learned from admitted reads or exact own commit readback, never from the cleanup's current occupant. A fresh adapter that has not observed an occupied slot returns mismatch. Identical ciphertext copied into a replacement creation is still a mismatch. Bounded digest witnesses retain metadata only. The first admitted slot creation and Vault identity are sticky: stale reads/authority refuse `POSTGRES_AUTHORITY_CHANGED`, and stale/changed-Vault writes refuse `REVISION_CONFLICT`. After deletion, rollback or a lost original incarnation, install a fresh adapter for a new generation instead of reusing the stale adapter.

For an ordinary committed transfer target, cleanup additionally compares the exact original revision-zero publication/operation/creation/storage/encrypted evidence and target binding, then conditionally deletes authority and writes its rollback tombstone in the same transaction. An advanced revision or unknown/missing/changed binding is mismatch. An actual missing authority with no custody is absent; a committed missing authority is mismatch. Exact retained rollback tombstone and missing authority is absent. Mismatch never removes a replacement occupant.

Prepared cleanup compares the locally submitted or constructor-pinned exact original proof and expected envelope. Its conditional SQL UPDATE includes operation, creation, storage, Vault, revision, digest, full envelope equality and actual SQL authority absence. It tombstones only the still prepared owned snapshot, retaining encrypted evidence. Reserved custody with no snapshot returns absent without rolling back the reservation. Already exact tombstoned ciphertext returns absent. Ordinary authority occupants, altered proof/generation/phase, unknown ownership and changed ciphertext return mismatch. No filesystem material is removed.

Both hooks must own their outer target SQL transaction. Readonly `adapter.hasActiveLease` identifies an active transaction in the current async context; `deleteIfCurrent` rejects `POSTGRES_LEASE_ACTIVE` inside that same target lease, rather than reacquiring a second client or claiming completion before its outer COMMIT. A held separate source lease is compatible. Ordinary load/commit/source leases remain reentrant. A missing mutation row count, SQL failure, lost acknowledgement or COMMIT rollback tag cannot return successful deletion. The prepared adapter updates its acknowledged cleanup state only after its owned transaction completes; an uncertain cleanup is retained for explicit inspection, with no automatic retry.

Coordinator composition must also arrange failed-open resource closure outside held admission: the existing adapter `close()` guard refuses close in its own lease, and shared Vault failed-open paths can call close there. That separate join concern is not changed or qualified by this cleanup repair.
