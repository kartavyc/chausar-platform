# Journal lifecycle in the existing renderer

The Decisions page keeps the simple decision form and adds **Create journal entry**. The rich form collects the complete journal content through ordinary labelled controls, using the existing styles. New business declarations start blank: statement, option labels/reasons, chosen option, current owner, review date, outcome measure/population/window/maturity/lag, assumptions, uncertainty and hypotheses. Option and assumption IDs are stable internal identities, never business presets. Users can add or remove options, assumptions and evidence rows.

Evidence selectors load current authorized dashboard calculation receipts plus the selected record's authorized retained snapshots. Accessible source filters narrow these choices; figure selectors come from the chosen receipt. The owner dropdown uses active members already exposed by `trust.get`. The current API exposes that list to owners/cofounders; if it returns no choices the form explains the limitation and does not invent an owner or broaden access. A future non-admin desktop owner picker needs a separately authorized API decision.

**Preview journal draft** calls `decisions.journal.draft` and displays readable content and exact receipt evidence without saving a record. The form stays available behind the preview so cancelling does not discard the proposal. **Confirm journal entry** is disabled until the user checks the explicit review consent, and its handler independently checks consent. Confirmation submits the displayed draft and its exact reviewed digest. Optional absent properties are omitted from payloads; the preview is converted to its plain JSON wire representation so inherited optional undefined receipt properties cannot break strict desktop IPC. This matches the journal digest's JSON identity.

Rich records use **Revise journal** with the loaded record revision and a required reason, and **Review journal** with an explicit outcome, observation state, notes, uncertainty, concurrent interventions, optional next review date and selected measured figures. The declared population/window/maturity/lag remain visible for review; changing them belongs to a content revision. Pending is an explicit observation choice. Measurements reference exact saved figures rather than user-entered money. Scenario projections are excluded from the measurement selector, consistent with the facade's existing refusal. Observation and achievement judgments remain human declared; exact figures do not establish causal impact or matching observation windows.

The optional execution selector loads currently readable `actions.list` records. It offers only unambiguous settled action/attempt pairs with matching verified readbacks and explicit matching business-success flags. Nothing is selected initially. Prepared, missing, mismatched or duplicate records are excluded; a forged selector value is refused before IPC. The current Engine resolver independently rechecks authority, registered operation, approval, ledger and exact readback at save time. A refusal keeps the selected reference and typed human assessment visible. The selector never executes or reconciles an action and never turns an effect readback into an achieved business outcome.

On `REVISION_CONFLICT`, the UI reloads currently accessible records, shows the current content and keeps every typed proposal/assessment field. It blocks further writer requests until the user explicitly selects **Use reloaded revision**, then requires another form submission. No automatic retry, overwrite or field merge occurs. If the record is no longer available under current access, the preserved form cannot adopt a guessed revision.

**Apply review filters** sends only explicitly supplied due date/branch to `decisions.journal.due`; blank filters include closed entries. **Show all decisions** reloads the authorized log and clears filters. **History** shows readable retained content, receipt figures, revisions/reasons and human-declared reviews/measurements/concurrent interventions, using text nodes throughout. Legacy simple records keep their original creation/review methods; rich rows use the named journal methods.

The Daily Brief's **Review** control uses the same revision-bearing record check as the Decisions page. Rich entries open the existing journal review form and submit `decisions.journal.review` with the loaded revision; simple records keep the legacy review form and `decisions.review` request.

## Scope and verification

Renderer changes are confined to `renderDecisions`, newly named journal helper functions and the Daily Brief decision-review handler. Conversation handlers, `renderAnswer`, other page sections, preload/IPC implementation, Engine, services, styles and dependencies remain outside this lane. For the Daily Brief follow-up, a source-boundary check permits only the rich/legacy dispatch expression in that handler and compares all remaining renderer source against base commit `93f34f8`, accounting only for Git's working-tree CRLF conversion.

They cover blank required declarations, current owner selection, stable distinct option IDs, filtered evidence, preview consent/digest, review measurements, revision and review conflicts, due filters, safe readable history and legacy flow. The existing eight renderer/composer/calculator/actual-worker regressions are included in the focused run: all 16 passed, zero skipped. Actual TypeScript 5.9.3 strict compilation also passed. No graphical browser, live provider, native inference or external effects are exercised; visual acceptance is not claimed by these DOM fixtures.
