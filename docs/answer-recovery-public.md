# Fresh calculation from a saved unpinned answer

This public recovery flow creates a **separate fresh calculation** from the filters and operation of an older saved request that lacks `asOf`. It does not reconstruct an unknown historical cutoff. The original saved answer and receipt remain unchanged. Keeping that unpinned original still blocks whole-workspace retrospective promotion with `TRIAL_REBUILD_REQUIRED`; this flow introduces no retirement or supersession policy.

All five routes require the current private owner, current permission epoch and an untainted desktop context. The original private receipt and source access are resolved from the actual store on every stage. Current connector acquisition/semantic readiness guards remain in force, including selected zero-row domains. HTTP JSON requests, actual desktop IPC allowlist and its TypeScript tuple use the same route names.

## Public contract

1. `answers.recovery.review { answerId }` resolves the exact original answer/receipt, discloses the unpinned status and returns `source`, `reviewedEvidencePin`, the original request without an invented cutoff, and the current dictionary hash/version. It chooses no new time values and writes nothing.
2. `answers.recovery.prepare { answerId, source, reviewedEvidencePin, timeScope, confirmedNewCalculation: true }` checks the reviewed original and current evidence again. `timeScope` must explicitly contain all four fields: `asOf` (ISO instant with offset), `period` (inclusive dates or explicit `null` for all event dates), `comparePeriod` (new comparison dates or explicit `null`), and `onDate` (new aging date or explicit `null`). Comparison and aging requirements depend on the retained operation. Unknown fields, missing fields, invalid calendar dates and caller-issued identities are refused. The host issues a durable `newRequestId` and exact `preparationDigest`; preparation does not calculate.
3. `answers.recovery.execute { newRequestId, preparationDigest }` uses that exact issued preparation. It rechecks original evidence, current owner/epoch, dictionary, facts/imports/identity rules, source access and acquisition readiness. It performs the normal calculator through a transaction-local `StateStore` with the configured verifier and connector guards rebound to the candidate view. The fresh receipt, fresh answer and completed lineage commit together through **one actual Vault revision/CAS**, without nested Vault operations or fabricated intermediate persisted revisions.
4. `answers.recovery.get { newRequestId }` independently resolves the durable request, original source and the separate fresh answer/receipt. Completed readback rebuilds and compares exact lineage, request and receipt digests under current access. A prepared request has no calculation result. A completed result is labelled `new-calculation-with-declared-time-scope`, `historicalReplay: false` and `grantsAuthority: false`.

5. `answers.recovery.list { answerId }` resolves current ownership and source access again and rediscovers issued requests for that original answer. It performs readback only. Completed rows return their exact fresh receipt and lineage; unavailable rows disclose a typed refusal without issuing or executing another request.

The issued control record lives in encrypted `State.answers` as `answer-recovery-request-v1`, separately from ordinary answer rows. Its integrity binds the issued plan, evidence pin, owner/epoch and eventual completed lineage. No historical identity or record is mounted as new authority.

`FactFilter.kinds` is a lower-level memory/projection field. Although the calculator's syntactic allowed-key list includes it, `CalculatorService.calculate` explicitly refuses any supplied `kinds` array; published definitions determine the counted kinds. Recovery therefore refuses a retained request containing that unsupported filter rather than dropping it or inventing kind-scope receipt evidence. The public regression deliberately authors such legacy state, including an explicit empty array, and proves typed refusal leaves all original bytes and authority unchanged with no partial preparation/receipt/lineage. It does not describe that fixture as a valid current-calculator-produced request.

## Retries and uncertain outcomes

Concurrent exact executions share one in-flight calculation. A completed exact retry returns the same retained answer/receipt without another write. Another digest or changed evidence is refused. No automatic execution retry occurs after an uncertain acknowledgement.

If calculation produced a candidate but the actual Vault commit throws, that handle marks the request `outcome-unknown` and refuses a second calculation. The owner must lock/reopen and call `answers.recovery.get` for the same issued ID. If the physical commit completed, reopen returns its one exact completed result. If durable authority remains prepared, readback describes a prepared request; an explicit subsequent owner action can execute it after current evidence checks. No partial fresh receipt is represented as completed lineage.

## Renderer

Conversation → **Older calculations** lists currently visible unpinned saved requests. **Review fresh calculation** opens empty time controls. The owner must choose the known-on timestamp and event-date scope explicitly, plus comparison/aging dates where applicable. The timestamp is sent as an explicit ISO offset instant; the renderer does not infer an old time, auto-select the current date, or perform a local-calendar/DST conversion. A second review displays the exact new request and current dictionary before **Create this fresh calculation**. The UI then retrieves the issued result with the public `get` route. It labels the result fresh and discloses the preserved original's retrospective-promotion limitation.

## Evidence and limits

`platform/tests/answer-recovery-public.test.ts` uses fresh synthetic encrypted Vault files and actual loopback HTTP. It covers current dictionary semantics, explicit scope, original preservation, one revision/receipt/lineage, whole-workspace retrospective refusal, invalid payloads, changed evidence, current owner/epoch/source access, actual unqualified managed-source refusal, concurrent exact retries, and a fault thrown **after the real encrypted adapter commit** followed by reopen/readback. After reopen, **Older calculations → Check earlier fresh requests** retrieves the same durable IDs and results without executing implicitly. Its renderer case executes the actual renderer/preload/strict structured-clone IPC through the real HTTP host. A separately labelled configured-verifier fixture checks wiring and refusal atomicity; it does not qualify native SQL.

This is local source integration evidence. It supplies no native database, installed desktop GUI, live vendor/model, hosted/enterprise, security review or complete-product qualification. Publication and aggregate qualification belong to the coordinator.
