# Reviewed local activation namespaces

`WorkspaceBackupV2LocalCustody` accepts the constructor-only capability `workspaceActivation: { journalVault, inspectCurrentLive? }`. It requires a separate already unlocked `experimental-file` Vault at one canonical direct child of the managed application directory. Source, journal and target locations must be distinct. This option is never an RPC field and does not authorize unrelated application siblings. An `outsideApplicationNamespaces` declaration still refuses an actual external sibling with `BACKUP_EXTERNAL_ENUMERATION_REQUIRED`; it cannot grant foreign workspace, credential or token reads.

The adapter acquires source then journal snapshots for the complete local operation. Root composition must use the same order and must not hold or reacquire an outer journal snapshot before source custody. `withHeldSource`, `withArchiveReader` and `withInertReader` retain their composition roles. The additional trusted `inspectHeldNamespaces()` method requires an existing source scope, checks current complete-owner admission before and after measurement, and returns physical identities, file hashes/byte measurements, directory identities and namespace dispositions. It returns no raw bytes or decrypted journal values. Root may compare these profiles at fully bound transaction boundaries; partial publication is not a complete profile.

The journal is authenticated separately through its own `Vault.captureEncryptedCustody`, using the explicit filesystem byte/count budgets. Its exact physical authority and every typed private ciphertext must match that capture. Unknown physical journal namespaces, private purposes or private entries refuse. Journal authority/private artifacts are measured outside the source archive; its writer lock is measured as transient process custody. Journal operator credentials and active keychain hooks remain explicit external dependencies. The archive still contains only the source authority and source private ciphertext, including source-issued reservations. No journal key or credential is exported, and no historical authority is mounted.

An actual `wit_<target-id-sha256>_reservation` permits namespace accounting only when its authenticated value has the exact v1 reservation shape, source Vault/workspace identity, artifact ID, distinct safe target ID and physical directory identity. An empty target is reported empty only after actual enumeration. A populated target requires one committed durable activation attempt whose reservation/ref, paired identity claim and identity ledger all agree. Every measured path must match its exact issued encrypted file or directory manifest; each file's physical generation, size and hash are rechecked. Arbitrary target descendants are refused before opening their files.

The only admitted activation administration section is `.workspace-activation-control/staging`. Every actual `attempt_<UUID>` directory needs a durable `Journal.staging: { name, physical }` binding retained from the journal CAS performed immediately after allocation. It must resolve to exactly one prepared or committed attempt, the source-owned target reservation, the durable ledger and its paired candidate claim. Prepared staging must contain the complete issued encrypted files and directories. Committed staging must contain exactly the retained empty directory manifest after publication. Staging directory entries are counted even when their byte count is zero; their physical identities are retained in the profile. The encrypted bootstrap/evidence copies must match their exact journal refs and ciphertext hashes. Only exact issued `live/.../*.encrypted.json` paths may be opened; wildcard ownership of an `attempt_*` subtree is never granted. Unknown sections, orphan names, attempted partial publication, added token files, replaced generations and inconsistent manifests refuse with typed activation-custody errors.

Ordinary v2 source pins compare the whole measured profile before and after custody, including the separately authenticated journal and owned staging/targets. Only the exact source controls written by that backup operation receive the existing controlled-change treatment. Journal mutations and wider filesystem changes therefore invalidate the source fence. Current complete-owner/source/readiness guards remain required throughout; a journal capability alone does not establish backend or external readiness.

Without `inspectCurrentLive`, this profile measures unchanged initial committed target ciphertext and refuses later authority revisions under the old manifest. A trusted constructor may supply `inspectCurrentLive({ context, targetId, publication }): Promise<void>` for the exact committed `encrypted-local-host` target. The publication is assembled from the authenticated original bootstrap/evidence journal refs, then checked against the durable record's original State, authority and evidence digests; its original nested State JSON order is preserved. It is private constructor data, never RPC State or a raw physical path. This capability is invoked before and after bounded measurement and must return `undefined`. Root must authenticate the actual newly created Vault with its fresh credential and pinned new Vault identity/workspace/sole fresh owner/epoch, check sealed business and policy, validate the exact original revision-zero digest when applicable, and admit only reviewed current synthetic runtime output/receipt revisions. The capability does not authorize other live profiles.

Only `live/main/authority.encrypted.json` may have a current physical generation, size and hash under this capability. The exact committed live-root physical identity and complete journal-issued layout remain mandatory; every other file, directory and immutable evidence ref retains its original checks. Unknown paths, links, unbounded files and incomplete layouts refuse before inspection or file opening. The current authority's measured bytes are re-read exactly after final authentication, so an inspection that changes or races the measured authority fails. Ordinary source fences still compare all current measured files before and after the operation; legitimate revisions are admitted between operations, never hidden as controlled in-operation changes. New live process locks or files, unsupported live layouts and unresolved attempted staging require separately reviewed custody or explicit root inspection. They are never silently omitted or represented as zero bytes.

This is bounded experimental source qualification. `fullWorkspacePortable` remains false, wider namespaces remain outside the archive, and these runtime/tests/doc changes do not independently qualify Engine/RPC wiring, activation publication, release, external custody, native storage or recovery.
