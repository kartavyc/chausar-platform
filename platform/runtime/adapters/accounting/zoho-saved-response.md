# Saved Zoho credit-note response slice

This adapter joins host-selected saved **Books v3 credit-note list JSON** to the existing `ConnectorReadDispatcher` and `ConnectorReadImportBridge`. The legacy `ingest.ts` `zoho-json` route imports invoices separately; the baseline Zoho v1 adapter has a captured-JSON parser and API reader, but no saved-response file reader. This slice reuses that exact v1 parser. It incorporates no inferred predecessor v2 changes, vendor CSV/PDF schema, credential provider or API call.

`createZohoSavedResponseAdapter` returns the public `ExportReadAdapter` contract (`export` / `file`, single attempt, dispatcher-owned retry, `files.read` authorization). The host injects `readFile(page, context)`, original UTF-8 bytes, content type and company/organization custody. The ordered `pageSha256` manifest is host configuration, never a field guessed from vendor JSON. Its hashes, company/dataset and parser revision contribute to `zohoSavedResponseConfiguration`. Qualify the export and subsequent import separately, with matching applicability. The manifest is bounded to 20 pages, each at most 4 MiB and subject to tighter dispatcher budgets.

The reader requires page 1 through an explicit native terminal page, with no missing or extra files. `parseZohoPage` checks the reported page and any embedded organization ID. Native bytes, including BOM and line endings, reach dispatcher SHA-256 provenance unchanged. File hashes and host labels alone cannot prove organization ownership or a coherent upstream snapshot. All source time, report totals and snapshot fields remain unavailable; pagination completion keeps source completeness `unknown`.

The existing `createAccountingDecoder` requires an explicitly reviewed currency precision and source measure. It preserves numeric lexemes, converts exactly to integer minor units, and refuses fractional minor-unit rounding. Credit documents retain positive totals, source status/balance, and existing missing-detail/tax warnings. They establish no cash refund or earned revenue. The test owner explicitly defines `recorded_credit_note_value` for synthetic arithmetic, accepts a data-only mapping, and supplies a separately hand-worked synthetic source report. Unaccepted or changed recipes require their own exact mapping review. Equivalent imports contribute once; decoder/schema/resource conflicts retain quarantine and block readiness.

All fixtures are newly authored synthetic data (generator revision `saved-creditnotes-fixture-1`); dates, IDs, amounts, custody and reports are invented. The two modeled list pages exercise exact large values and decimal precision: `9007199254740993.0100 + 0.0900`, independently totaled as `900719925474099310` INR minor units. They omit vendor installations, country tax behavior, real source clocks, coherent snapshots, corrections and deletions. No synthetic evidence qualifies sandbox/live use. Matched totals support this arithmetic demonstration while default `assertReady` still refuses `SOURCE_NOT_READY`.

## Real-sample qualification requirements

1. Lawfully obtained, owner-authorized original first/middle/explicit-terminal credit-note list JSON from the **same** organization, with canonical company custody, exact Books API version, data center, country edition and relevant configuration. Saved response labels do not prove custody; ordinary payloads omit organization IDs.
2. Response status/content type, original byte lengths/SHA-256, acquisition target, page size, filters/visibility, capture/run correlation and a reviewed complete artifact manifest. Demonstrate pagination under a moving collection or retain its consistency limitation. Missing, filtered or cross-run pages must refuse completeness.
3. Real source IDs, dates, currencies, positive totals, balances and actual status variants (including draft/void/unknown and partial/applied credits where available); missing amount/currency, optional-field and number/string changes. Matched detail samples and independent review are additionally required for line, tax or invoice-allocation claims.
4. An independently reviewed source credit report with report ID/SHA-256, exact row count and integer minor-unit total for the same company, dataset, branches, period and currency. Source observation and coherent snapshot evidence must accompany the report/acquisition; matching sums or a local read timestamp cannot establish them.
5. Explicit owner acceptance of source measure, event/status interpretation, currency precision, decoder definition/native wire fingerprint and exact recipe revision. Admit retention/evaluation rights, independent golden cases/disjoint installation holdouts, current semantic gate evidence and the durable ledger anchor before serving a certified receipt.
6. Separately controlled before/after correction and deletion samples with independent source reads if those capabilities are requested. This v1 parser retains available revision text but qualifies neither ordered corrections, deletions, whole-organization completeness nor bank settlement.

Schema references already reviewed in the repository are the official [credit-notes API](https://www.zoho.com/books/api/v3/credit-notes/) and [pagination](https://www.zoho.com/books/api/v3/pagination/), documented in `docs/accounting-zoho.md`. This task performs no new source acquisition and redistributes no vendor examples.
