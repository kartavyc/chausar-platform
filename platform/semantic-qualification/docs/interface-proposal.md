# Semantic qualification interface v1

This lane owns only `platform/semantic-qualification/`, based on local `100df1d3c3bdb8e7793d81e6590cd6145c617d3e`. Integration is owned by the parent. No shared runtime, ontology, connector, database, root manifest or CI changes are proposed here.

The proposed integration boundary is `src/contracts.ts` and `src/index.ts`:

- `compileMapping(pack, companyRules, ontology)` validates strictly data-only, versioned contracts and exact product configuration, and returns immutable fingerprinted bindings. A product pack has no company overrides. Company rules name the pack hash, company, branch, tax registration, currency scales and rational unit conversion rules.
- `mapBatch(compiled, sourceBatch)` validates exact schema, typed records, explicit semantic states and source receipt hashes before deriving canonical facts. A mapping is invalidated by schema, product, ontology or rules drift. Ambiguity abstains with one clarification; no partial facts escape.
- `qualifyCase({ compiled, batch, report, manifest, provenance, artifactBytes, splitPlan, goldenCase, at }, ledger)` performs rights/personal-data/artifact/split admission before mapping, reconciles source row coverage and per-kind/per-currency net, tax and gross controls against a separately captured source report, and checks independent per-row identity/date/currency/unit/link/exclusion assertions and operation expectations. It evaluates declared operations with BigInt and appends hash-linked evidence per operation. Admission failures throw `SemanticError` without retaining source-bearing ledger records. Any admitted semantic failure abstains atomically; schema/product drift invalidates.
- `verifyLedger(ledger, expectedHead)` detects changes, reordering and truncation relative to an independently retained head. Without that anchor it verifies internal links only. `checkEvidenceCurrent(evidence, current)` verifies the receipt's own hash and prevents reusing evidence against changed mapping/schema, source rows/snapshot, report, rights/provenance manifest, split or golden hashes. Ledger hashes are tamper evidence, not a publisher signature or secure storage.

Database/compiler lane: consume `CanonicalFact` (net/tax/gross money strings with explicit currency scale, dated business event kind, quantity/unit, original source row and receipt hashes). Operations and ontology remain supplied data with exact version/hash. This prototype implements seven fixed deterministic register operations; it does not replace the production ontology compiler, CEL evaluator or SQL compiler. It accepts no executable SQL, formula, script or arbitrary expression.

Connector lane: supply complete source batches with an explicit product/version/edition/configuration, declared raw schema, original receipt ID, canonical row-set SHA-256 and stable snapshot ID. Supply a separate upstream control report with the same company, branch, tax registration, period/date basis and snapshot. A control report must never be generated from the mapped output. The harness cannot authenticate an upstream publisher solely from an operator-supplied hash.

Qualification is company/operation/snapshot-specific. Synthetic fixtures, including separately authored public synthetic holdouts, cannot become real installation or arbitrary unseen-company qualification. The current executable admission gate supports only the authored `synthetic-register` profile; all named systems remain blocked pending native profile implementation and qualification. User-owned samples need explicit qualification rights and personal-data review. Writes remain unqualified pending the user's operation selection and the connector lane's approval/readback contracts.

The exact roster is the original plan's 50 groups plus the six user additions, recorded in `fixtures/connector-groups.json` as 56 groups. Original groups combine products/variants differently from the recovered runtime catalogue's 50 entries. QuickBooks remains included. No operation is raised to qualified by roster membership.

Split entries include separate business, template and configuration origins. All three families must be disjoint across tuning and holdout, including alternate exports of a business. The split is frozen per product/compiler fingerprint; distinct independent templates can be checked by the same deterministic compiler against their own reviewed pack, with company-specific evidence. These are public synthetic compiler tests, not a measured model's unseen-company onboarding performance.

`received` counts included settled payment gross amounts (including tax), following the recovered ontology's cash-receipt meaning. Other money measures use net amounts excluding tax. Currency scales are evidenced company accounting configuration, not an ISO currency-table certification. Bank balances, settlement fees/netting, FX, accrual recognition, cross-period refunds, revision replacement and vendor-specific semantics require additional contracts and business cases before use.
