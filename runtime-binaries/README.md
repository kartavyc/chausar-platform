# Vendored native runtimes

This directory deliberately contains no PostgreSQL, Python or native custody executable. The preview uses an explicitly selected experimental file vault; production PostgreSQL does not fall back to a database installed on the developer's machine. A native release must vendor genuine, licensed runtimes for each supported target and pass `node scripts/package-preflight.mjs` before invoking electron-builder.

Assemble one target platform and architecture per package checkout directly under this directory. The manifest declares that target, such as `win32` with `x64` or `darwin` with `arm64`. Runtime startup uses `process.resourcesPath/runtime-binaries` in the installed app. Required paths relative to this directory are:

| Component | Windows | macOS/Linux |
| --- | --- | --- |
| PostgreSQL server | `postgres/bin/postgres.exe` | `postgres/bin/postgres` |
| PostgreSQL initialization | `postgres/bin/initdb.exe` | `postgres/bin/initdb` |
| PostgreSQL control | `postgres/bin/pg_ctl.exe` | `postgres/bin/pg_ctl` |
| PostgreSQL upgrade (major-version moves) | `postgres/bin/pg_upgrade.exe` | `postgres/bin/pg_upgrade` |
| Previous PostgreSQL major, kept for one upgrade | `postgres-<major>/bin/…` | `postgres-<major>/bin/…` |
| Python interpreter | `python/python.exe` | `python/bin/python3` |
| PDF readers (pdfplumber, pypdfium2, Pillow and dependencies) | `python/Lib/site-packages/…` | `python/lib/python3.13/site-packages/…` |
| OCR program, its libraries and English data | `tesseract/bin/tesseract.exe`, `tesseract/share/tessdata/eng.traineddata` | `tesseract/bin/tesseract`, `tesseract/lib/…`, `tesseract/share/tessdata/eng.traineddata` |
| PDF reader record (read by `platform/runtime/native/reader-bundle.ts`) | `readers.json` | `readers.json` |
| Direct vault custody helper | `keychain/chausar-keychain.exe` | `keychain/chausar-keychain` |

Ship the complete runtime, including dependent libraries, PostgreSQL share files, Python standard library and license notices. Native files must match the declared architecture. Use real directories and regular files without symbolic links. On Unix, unpack genuine Python symlinks into a regular interpreter file and retain executable permissions. Do not add placeholders or substitute PATH commands.

Build the direct custody helper from [`platform/native/keychain`](../platform/native/keychain/README.md) with the target SDK and native dependencies. Windows uses `advapi32`; macOS uses Security/CoreFoundation; Linux needs libsecret-1 and GLib/GIO >= 2.50 plus a qualified existing native Secret Service keyring. Coordinate missing dependencies and native execution with the parent release task. This source change does not acquire packages, launch credential stores, change access policies or qualify an OS provider.

The helper requires a separate `keychain/manifest.json` with exactly `format: "chausar.keychain-helper.v1"`, `platform`, `architecture`, `executable` and `sha256`. The executable is exactly `chausar-keychain.exe` on Windows or `chausar-keychain` elsewhere; the lowercase SHA-256 comes from the final signed helper bytes. Platform is `win32`, `darwin` or `linux`; architecture is `x64` or `arm64`, matching the running host. Ship one native executable for that target (thin Mach-O on macOS). Inventory this manifest, helper, dependent libraries and licenses in the outer runtime manifest. Its existing `components` schema remains `postgres` and `python`; the custody helper's provenance, signing and native acceptance must also be qualified by the parent release process. The current preflight is not an OS keychain acceptance test.

Production desktop startup supplies the fixed packaged custody manifest path; the worker refuses readiness if this configured manifest or helper verification fails. No credential-store call occurs during manifest verification. Keep the signed helper and every ancestor directory protected from replacement. Unix verification rejects unsafe ownership/modes and symlinks; Windows ACL proof and the verification-to-launch pathname race still require native package qualification. Never substitute a script, PATH command, unsigned placeholder or file-backed custody provider.

Obtain PostgreSQL through the [official download entry point](https://www.postgresql.org/download/) and Python through the [official download entry point](https://www.python.org/downloads/). Record the actual package vendor and distribution source; do not invent official builds for unsupported combinations. Review redistribution licensing, validate the vendor's download integrity independently, and test the native runtime on the target operating system.

This directory requires a `manifest.json` with exactly these top-level fields: `schemaVersion: 1`, `platform`, `architecture`, `components` and `files`. `components` has exactly `postgres` and `python`. Each component records an exact vendor `version` (for example PostgreSQL's two-part release or Python's three-part release), public HTTPS `source`, SPDX or descriptive `license`, and relative `licenseFile`. `files` lists every regular bundled file other than the manifest itself, including this README if retained in the package. Each entry has exactly a relative POSIX `path`, lowercase 64-character `sha256` and integer byte `size`. Paths cannot contain parent traversal, drive letters or backslashes. The license files belong in this inventory too. Generate hashes from the real runtime distribution; an inventory generated from a placeholder is not an acceptable release artifact.

`scripts/package-preflight.mjs` is read-only. It rejects missing native binaries, invalid platform formats, incomplete inventory, changed bytes, symlinks, missing helpers, missing exact npm dependency lockfile and absent signing prerequisites. It never downloads runtimes, creates a synthetic lockfile, initializes a database or executes an installer. The gate is a prerequisite check and cannot qualify a vendor's provenance or a signed installer by itself.

The publisher must supply `CHAUSAR_RELEASE_PRIVATE_KEY_FILE` and `CHAUSAR_RELEASE_PUBLIC_KEY_FILE` as absolute Ed25519 PEM paths. Keep the private key outside the source repository. Windows and macOS additionally require an absolute local signing certificate path in `CSC_LINK` and a `CSC_KEY_PASSWORD` in the release environment. macOS also requires `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD` and `APPLE_TEAM_ID` for notarization. Keep all private credentials in the release operator's protected environment; never commit them. The preflight checks key ownership without printing key material. The native signing and notarization tools must separately validate the certificate and produce a signed artifact.

The native credential names follow the [pinned electron-builder 26 signing documentation](https://www.electron.build/v26/docs/features/code-signing/). This project's gate selects local certificate files and refuses missing publisher credentials; electron-builder offers additional signing backends that would require their own explicit configuration and validation.

The release pipeline must run the preflight and stop on its nonzero exit status, then run electron-builder with signing enabled. For example, in PowerShell, run `node scripts/package-preflight.mjs`; if `$LASTEXITCODE -ne 0`, stop before packaging. A source build from `scripts/build.mjs` is explicitly an unsigned preview and does not satisfy this gate.

Desktop startup is wired to launch the bundled PostgreSQL binaries on loopback when no explicit PostgreSQL URL is configured, using a private generated password file. The packaged Python path is explicit. The native runtimes are absent in this environment, so this wiring has not been qualified with a native launch. Before claiming an installed production release, verify startup and orderly shutdown on each target, test the Python helper process restrictions, sign the actual release manifest with the publisher's pinned Ed25519 key, and prove backup/rollback across an upgrade. Those qualifications are not asserted by this source tree.

## Staging (release lane)

`node scripts/release/stage-runtime.ts --platform <win32|darwin|linux> --arch <x64|arm64> --out runtime-binaries` downloads the pinned archives listed in `scripts/release/runtime-sources.json`, checks each SHA-256 pin, lays the files out as above, optionally signs native files with `--sign-command`, and writes `manifest.json` in the preflight schema. Only `linux-x64` is pinned so far (PostgreSQL 17.6 from theseus-rs and Python 3.13.7 from python-build-standalone, each matched against the publisher's own checksum file, recorded in `checksumSource`); every other pin is `null` until the release operator verifies it, so staging those targets refuses with `RUNTIME_SOURCE_UNPINNED`. A layout's optional `exclude` list leaves out symlinked duplicates (the Linux Python's `bin/python` and `lib/libpython3.13.so`) that would otherwise be materialised as extra copies of 113 MB and 246 MB files. `--inventory-only` re-inventories an assembled directory (for example after the keychain helper is added). Staged runtimes are never committed; `runtime-binaries/.gitignore` keeps them out. The bundled cluster's lifecycle (initdb, start, stop, port, crash recovery and the `pg_upgrade` path) is `platform/runtime/native/postgres-lifecycle.ts`. `node scripts/release/verify-postgres-linux.ts --stage <dir> --old-bin /usr/lib/postgresql/16/bin --as-user <account>` stages the Linux runtime and runs that lifecycle against the real binaries, printing a JSON receipt; PostgreSQL refuses to run as root, so as root the checks run under `--as-user` through `runuser`. The Linux PostgreSQL build links the system's `libssl.so.3`, `libcrypto.so.3`, `libxml2.so.2`, `libzstd.so.1`, `liblz4.so.1`, `libgssapi_krb5.so.2` and `libz.so.1` and needs glibc 2.34 or newer; those are not vendored, so a target without them cannot start the bundled database.

### PDF readers (FR-07)

`node scripts/release/stage-runtime.ts --platform <p> --arch <a> --out <dir> --readers-only [--replace]` adds the PDF readers to an already-staged runtime (`--readers` does it as part of a full stage), then re-signs and re-inventories it. Pins are the `readers` section of `scripts/release/runtime-sources.json`: the Python packages come from `scripts/release/reader-requirements/<target>.txt`, installed by the staged interpreter's own pip with `--no-deps --only-binary=:all: --require-hashes` (one wheel per package; each hash equals PyPI's JSON API digest) into its site-packages and byte-compiled with checked-hash `.pyc` files; tesseract comes from conda-forge `.conda` packages pinned by their repodata SHA-256, of which only `bin/tesseract`, its shared-library closure (glibc excluded; the binaries carry `RPATH $ORIGIN/../lib`, so no `LD_LIBRARY_PATH` is needed), `share/tessdata/configs/tsv` and every package's licence files are kept; `eng.traineddata` is pinned separately from tesseract-ocr/tessdata_fast. Staging runs on the target platform only (`READER_STAGE_HOST_ONLY`). Only `linux-x64` is staged and run; the other targets' pins are recorded but their `include` closure is `null`, so they refuse with `READER_SOURCE_UNRESOLVED`. The helper (`platform/helpers/analytics.py`) uses `tesseract/bin/tesseract` beside its interpreter (a regular file whose real path stays inside the runtime folder) with `TESSDATA_PREFIX` set to the bundled `tesseract/share/tessdata`, and otherwise falls back to the system default path.
